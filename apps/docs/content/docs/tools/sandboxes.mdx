The sandbox produces the dynamic evidence: the process tree, network activity,
the sandbox's own signatures, dropped files, registry and the rest. The
`dynamic` analyst reads that report through in-process tools, with no transport
to open, and the `network` analyst reads its capture. `core.sandbox.provider`
picks the provider; a job can pick its own with `sandbox_provider`.

The triage pack states the report's sections and how many items each holds
(`sandbox_sections`), or why the report does not carry one, and the
`sandbox_items` tool answers the items of a section whole, each with an id
such as `proc:84` or `net:3` and the report fields it came from, filtered by
pid, a substring, a signature or a list of ids. The `dynamic` analyst has it
with the other sandbox tools and the `network` analyst has it on its own (the
whole set where its definition asks for the sandbox tools); a claim cites an
item by its id, in brackets or in its evidence field. See
[the triage pack](/architecture/#the-triage-pack).

| Provider | Detonates | Reached at |
| :-- | :-- | :-- |
| `mock` (default) | nothing | — |
| `cape2` | on your CAPEv2 instance | `sandbox.cape2.base_url` |
| `triage` | on Hatching Triage's cloud | `sandbox.triage.base_url`, `https://tria.ge/api/v0` by default |
| `upload` | nothing of its own: reads a report produced elsewhere | — |
| `rest` | on any HTTP sandbox you describe | `sandbox.rest.base_url` |

<Callout type="warn" title="A sandbox runs the sample">

Point Maljan only at a sandbox you are authorised to use, on a network
isolated from production. What a submission discloses depends on the
service: a cloud sandbox holds the sample under its own terms.

</Callout>

## Mock

The default executes nothing. It returns a recorded fixture for a sample it has
one for, marked `recorded_fixture`, and an empty stand-in marked `synthetic` for
any other. Where no sandbox ran, the triage pack writes one `sandbox_status`
entry with the sentence that says so, the dynamic and network analysts are
skipped, the run carries the reason, and a stand-in's empty sections are never
rendered as "0 processes". See [Providers](/architecture/#providers).

## CAPEv2

| Setting | Default | Notes |
| :-- | :-- | :-- |
| `sandbox.cape2.base_url` | `http://localhost:8000` | The CAPE REST API. |
| `sandbox.cape2.api_token` | empty | Stored encrypted. |
| `sandbox.cape2.timeout_seconds` | `300` | How long to wait for the report. |
| `sandbox.cape2.poll_interval_seconds` | `10` | |
| `sandbox.cape2.package_by_format` | `{}` | A file type to a CAPE analysis package, e.g. `{"apk": "apk", "elf": "generic", "pdf": "pdf", "ooxml": "doc"}`; `*` is the fallback, and a format with no entry is submitted without a package so CAPE picks one. |
| `sandbox.cape2.submit_options` | `{}` | Sent verbatim as further form fields (`machine`, `tags`, `options`, `timeout`, anything `tasks/create/file` accepts). |
| `sandbox.cape2.mcp` | disabled | An optional CAPE MCP server beside the REST API. |

The guest platform is sent when CAPE has a name for it (`windows`, `linux`,
`android`) and left unset otherwise. An APK detonated with the `exe` package
produces nothing, which is what `package_by_format` is for.

## Hatching Triage

| Setting | Default | Notes |
| :-- | :-- | :-- |
| `sandbox.triage.base_url` | `https://tria.ge/api/v0` | |
| `sandbox.triage.api_token` | empty | Stored encrypted. |
| `sandbox.triage.profile` | empty | The VM profile; empty means the account default. |
| `sandbox.triage.profile_by_format` | `{}` | A file type to a VM profile, with `*` as its fallback and `profile` behind that, so an APK reaches an Android profile. |
| `sandbox.triage.analysis_seconds` | unset | How long the VM runs the sample, sent as `defaults.timeout`; unset leaves Triage's own default. |
| `sandbox.triage.timeout_seconds` | `900` | How long the platform waits for the report. Must be longer than `analysis_seconds`, and validation refuses one that is not. |
| `sandbox.triage.poll_interval_seconds` | `15` | |
| `sandbox.triage.fetch_pcap` | `true` | Fetches the capture for the network analyst. |

A value the account does not allow is refused by Triage, and the submission
error quotes Triage's own words and names the setting. The run summary states
the run-time limit Triage set for the task: a limit, not a measured duration.

## An uploaded report

The `upload` provider reads a report produced elsewhere instead of detonating:
attach it to the sample with `POST /api/v1/samples/{sample_id}/sandbox-reports`,
then name it on the job with `sandbox_report_id`, which also selects this
provider. CAPEv2, Cuckoo and Triage formats are accepted by default
(`sandbox.upload.allowed_formats`), up to 64 MiB (`sandbox.upload.max_report_bytes`).
Only a report attached to the job's own sample is read. See [Running an
analysis](/usage/running-an-analysis/).

### Report formats are declarations

Each report format is declared as data. Every sandbox provider and the upload
route read the declaration, never a format's name:

| Field | What it says |
| :-- | :-- |
| `name` | The format's name: a lowercase word of at most 32 characters, the width of the upload row's column (`unknown` is reserved). It is what the upload row records and what `allowed_formats` lists. |
| `detect` | How a payload is recognised: a list of groups of field tests, and the format matches when every test of any one group holds. A test is `{path, types, non_empty, contains}`: the value at `path` must be one of `types` (`object`, `array`, `string`, `number`, `boolean`, `null`), non-empty, or hold `contains` in its text (a string, number or boolean, compared without regard to case). |
| `task_id_paths` | Where the source sandbox's task id sits; the first string or number (not empty text) a path names wins. Any other value (an object, a list, a boolean, null) counts as absent. |
| `target_sha256_paths` | Where the report's claimed target sha256 sits; the first non-empty string or number wins. It is compared with the sample's hash, and a mismatch is a warning, not a refusal. |
| `reader` | Which report reader reads the format into the internal sandbox report: `cape2`, `cuckoo`, `triage`, or empty for a format no reader reads yet. An upload of a format with no reader is refused (422) with a message saying so. |
| `signature_scale` | What a signature's severity number means: `{name, rungs}`, the rung of the severity ladder (Informational, Low, Medium, High, Critical) each score from 1 up names. Absent where the format documents no scale. |

Field paths are the tool declarations' JSON-pointer-like paths (`/` keys and
`*` for every item), read in time linear in the report. `**` (any depth) is
refused when the setting is saved: recognising a report and finding its id
need only anchored places, and a whole-tree walk per test would make every
upload cost a multiple of the report's size. The upload route runs the reads
in a worker thread, off the API's event loop. The built-in declarations
reproduce what the platform always recognised:

| Format | Recognised by | Task id | Target sha256 | Signature scale |
| :-- | :-- | :-- | :-- | :-- |
| `triage` | `/analysis` an object and `/tasks` a non-empty object or array | `/sample/id` | `/sample/sha256` | Triage 1–10: 1 Informational, 2–5 Low, 6–7 Medium, 8–9 High, 10 Critical |
| `cape2` | `/CAPE` an object or array, or `/info/version` naming "cape" | `/info/id` | `/target/file/sha256`, then `/target/sha256` | CAPE 1–3: Low, Medium, High |
| `cuckoo` | `/behavior` an object and `/info` a non-empty object | `/info/id` | `/target/file/sha256`, then `/target/sha256` | Cuckoo 1–3: Low, Medium, High |

Declare your own in `sandbox.report_formats` (a JSON list), and add each new
name to `sandbox.upload.allowed_formats` to accept its uploads. A new format
must say how it is recognised (`detect`), and it is tried before the built-ins,
so a report shaped like Cuckoo but carrying your marker is yours. A
declaration under a built-in's name is merged over that built-in field by
field: a field you set replaces the shipped value, a field you leave out keeps
it. So `{"name": "cape2", "signature_scale": {...}}` changes CAPE's scale alone,
for live CAPE runs, REST reports in the CAPE format and uploads alike. For
example, a CAPE-shaped export whose ticket and digest sit elsewhere:

```json
[
  {
    "name": "acme",
    "detect": [[{"path": "/producer/name", "contains": "acme"}, {"path": "/run", "types": ["object"]}]],
    "task_id_paths": ["/run/ticket"],
    "target_sha256_paths": ["/subject/digests/sha256"],
    "reader": "cape2",
    "signature_scale": {"name": "Acme 1–4", "rungs": ["Low", "Medium", "High", "Critical"]}
  }
]
```

`GET /api/v1/sandbox-report-formats` serves every format in the order a
payload is tried against them, with its declaration and scale.

An uploaded report's format is recorded on its row when it is accepted, and the
run reads the report as that format; it is never sniffed again. If the
recorded format has since been removed from the declarations, or declared
without a reader, the job stops with a message saying so.

### Signature scales on the run

The scale a run's signatures are read on is the one its sandbox provider
declares for the report it read: the `signature_scale` of the report's format
among the declarations (a live CAPE or Triage run and a REST report in a
built-in format take that format's, merged with any declaration under its name;
an uploaded report takes its recorded format's), or for a `generic` REST report
`sandbox.rest.report.signature_scale_rungs` and `signature_scale_name`. The
worker records it on the run summary as `sandbox_signature_scale` (`null` where
none is declared), and the console's Dynamic tab colours and names each
signature's number by it. A run recorded before scales were has no such key and
is drawn as it always was, from the sandbox provider in its settings snapshot.

## Any REST sandbox

The `rest` provider describes a sandbox Maljan has never heard of, rather than
coding it:

| Block | What it says |
| :-- | :-- |
| `sandbox.rest.auth` | The header, scheme and token the API takes. |
| `sandbox.rest.submit` | The multipart submission (`method`, `path`, `file_field`, `extra_fields`, `submit_fields`) and the JSONPath of the task id in its answer. |
| `sandbox.rest.status` | The poll path, the JSONPath of the state, and the done and failed values. |
| `sandbox.rest.report` | Where the report is, its format (`cape2`, `cuckoo`, `triage` or `generic`), an optional capture path, and for a `generic` report its signature scale (`signature_scale_rungs`, `signature_scale_name`). |
| `sandbox.rest.mapping` | For a `generic` report, an RFC 9535 JSONPath per channel: processes, calls, signatures, DNS, HTTP, TCP, UDP, hosts, domains, dropped files, registry. |

An empty path in `mapping` says the sandbox does not publish that channel, and
the report lists it as unavailable rather than reading like a clean sample by
omission. `mapping.channels` maps a channel name of your own to a JSONPath for
anything the schema has no field for; namespace it by platform, e.g.
`{"android.permissions": "$.apk.permissions[*]"}`. See [Format routing and the
sandbox](/configuration/#format-routing-and-the-sandbox).
