containers that open the sample are kept apart. For the meaning of individual

## The compose stack

[`docker/docker-compose.yml`](https://github.com/Root0ne/Malspark/blob/dev/docker/docker-compose.yml)
is the production
shape. `docker/docker-compose.dev.yml` is an overlay that swaps the frontend to
`next dev` and supervises the worker so source edits take effect; `make dev-up`
applies both.

Only the console and the API need to face users. Every port binds to
`BIND_ADDRESS`, `127.0.0.1` by default. Each container that opens the sample
sits on an internal network with no gateway; a small relay publishes its port
for a worker that runs on the host.

builds `malspark-backend` once rather than once per service.

### MinIO, built from source

MinIO publishes its releases as source only, and the `minio/minio` image the
stack used to pull is no longer served by its registry. Compose therefore
builds the server: `docker/Dockerfile.minio` clones the pinned release tag,
stops the build if the tag is not the pinned commit, compiles it with a Go
release that still gets upstream fixes (the release's `go.mod` names only a
floor, Go 1.24), and copies the binary and its licence
onto a small Alpine image tagged `malspark-minio:<release>`. The first `up`
builds it (a few minutes, with network access to GitHub and the Go module
proxy); later ones reuse it. The Go stage cross-compiles for the target's
architecture, so the same file builds linux/amd64 and linux/arm64; it needs
BuildKit, which Compose and `docker buildx` use. The healthcheck asks the
server's `/minio/health/live` with the image's busybox `wget`. The server runs
as root, as the pulled image did, because an existing `minio_data` volume
holds files root wrote.

MinIO is licensed under the GNU AGPLv3. The repository ships a Dockerfile that
builds the unmodified upstream source of the named release, not a modified or
redistributed binary; the image carries the release's `LICENSE` and `CREDITS`
under `/licenses` and names the source and commit in its labels. An operator
who publishes an image built from it passes those on with it.

Ordering is explicit: `migrate` waits for a healthy Postgres, the API waits for
`migrate` to exit successfully and for Postgres and Redis to be healthy, and the
worker waits for the API's own healthcheck on top of that. Nothing waits for a
tool server or a vector store: a job whose team needs a static provider that is
not ready is refused with the agent and the address, and a memory backend that
is unavailable is reported and the run goes on without it.

### Running without Ghidra or Qdrant

`ghidra-mcp` and `qdrant` run under the Compose profiles `ghidra` and `qdrant`.
The shipped `docker/.env.example` turns both on (`COMPOSE_PROFILES=ghidra,qdrant`),
so a default install runs them exactly as before; a `docker/.env` copied before
this line existed needs it added, or neither starts on the next `up`. `make
docker-down` and `make dev-down` stop every profile's services whatever the
line says.

To run without one, take its name out of `COMPOSE_PROFILES` (an empty value
runs neither); its token is then not needed, and nothing else waits for it. The
stack starts and runs a job once two settings follow: select the static
analyser you do run (radare2, capa and YARA, a tool server of your own through
`generic_mcp`, or `none`) as `core.static.provider`, and, without Qdrant, set
`core.memory.backend` to `memory`. The shipped backend is `qdrant`, so until
then every run reports long-term memory unavailable and goes on without it.

## Apple Silicon (arm64)

Malspark runs on an Apple Silicon Mac with the same compose file. The core
services (`backend-api`, `backend-worker`, `enrichment-worker`, `frontend`,
`minio`, `postgres`, `redis`, `qdrant`) build or pull native arm64 images. The
services whose image carries an x86-64-only program declare
`platform: linux/amd64` and run emulated, slower than native:

| Service | Why it is x86-64 only |
|---|---|
| `ghidra-mcp` | Ghidra's release ships no `linux_arm_64` decompiler. |
| `die-mcp` | DIE's amd64 `.deb`. |
| `goresym-mcp` | GoReSym's x86-64 Linux build. |
| `yarax-mcp` | yara-x's x86_64 Linux build. |
| `webcrack-mcp` | Node's `linux-x64` build. |
| `unblob-mcp` | sasquatch's amd64 `.deb`. |
| `jadx-mcp` | Temurin's x64 JRE. |

On an amd64 host the `platform:` lines change nothing.

One program inside a native image is x86-64 only as well: FLOSS, the analysis
server's emulating string decoder, is FLARE's x86-64 Linux build, and the
backend image installs that build whatever its architecture. On an arm64
backend it may not run there (whether it does depends on the x86-64 emulation
the VM offers native containers); the analysis server asks the build its
version and reports the `floss` tool unavailable, with the reason, when it
does not answer. Every other tool runs as usual.

**Rosetta is required.** The emulated services need Rosetta, not Docker's
default QEMU user-mode emulation: under QEMU some multi-threaded programs crash
(GoReSym among them), so a sidecar starts and then fails its calls. In Docker
Desktop, turn on *Use Rosetta for x86_64/amd64 emulation on Apple Silicon*
under Settings → General. With Colima, start the VM on Apple's virtualisation
framework with Rosetta:

```bash
colima start --vm-type vz --vz-rosetta --memory 32 --cpu 8
```

**Give the VM 24–32 GB of memory.** The default profiles' ceilings alone pass
16 GB: the worker is capped at 8 GB, `ghidra-mcp` at 6 GB (`GHIDRA_MEM_LIMIT`)
and `enrichment-worker` at 2 GB, on top of PostgreSQL, Redis, MinIO, Qdrant, the
API and the frontend. A VM smaller than the sum has the kernel's OOM killer
stop a container mid-analysis. Each sidecar profile you turn on adds its own
memory ceiling.

**A model server on the Mac.** The worker reaches a model server on the host at
`host.docker.internal`. Ollama and LM Studio listen on `127.0.0.1` by default,
which a container cannot reach; make the server listen on all interfaces, for
Ollama with `OLLAMA_HOST=0.0.0.0` in the environment it starts from, for LM
Studio with *Serve on Local Network* in its server settings. The server then
also answers every machine that can reach the Mac: keep the macOS firewall on,
or block the port from other hosts, since neither server asks for a key by
default.

Native arm64 images for every service are planned.

## Required secrets

Every secret the core services need is declared with `:?`, so the stack
refuses to start — with the variable named — while any is missing. There is no
baked-in default for any of them. Ghidra's and Qdrant's tokens are not guarded
that way, since Compose reads every service's variables whether its profile is
on or not and a guard would stop a stack that runs neither: with its profile on
and its token missing, that one container exits, restarts under its restart
policy (`docker ps` shows it "Restarting") and logs the variable to set, and no
other service is stopped by it.

| Variable | Used by |
| :-- | :-- |
| `POSTGRES_PASSWORD` | The database, and the `DATABASE_URL` Compose assembles. |
| `REDIS_PASSWORD` | `--requirepass` on Redis, and the API and worker URLs. |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | MinIO, and the API's MinIO credentials. |
| `JWT_SECRET_KEY` | Signs API session tokens. |
| `SETTINGS_ENCRYPTION_KEY` | Encrypts secrets in the settings store. |

| Variable, with its profile on | Used by |
| :-- | :-- |
| `QDRANT_API_KEY` (`qdrant`) | `QDRANT__SERVICE__API_KEY` on Qdrant; without one it exits and restarts. |
| `GHIDRA_MCP_AUTH_TOKEN` (`ghidra`) | The bearer token the Ghidra MCP container requires; without one it refuses to bind and restarts. |

Optional knobs with defaults: `BIND_ADDRESS` (`127.0.0.1`), the published
ports, `RUN_MIGRATIONS_ON_STARTUP`, `CORS_ORIGINS`, `COOKIE_SECURE`,
`WORKER_RSS_RESTART_MB`, `MALSPARK_EMBED_THREADS` and `MALSPARK_EMBED_BATCH`.

Every published port binds to `BIND_ADDRESS`, which the example file sets to
`127.0.0.1`. The stack is unreachable from the network until that is changed
deliberately, behind a firewall or a reverse proxy you control.

The API, the workers and the migration mount `src/`, `apps/`, `tests/` and
`services/` read-only, and the API runs without `--reload`. A process in those
containers opens hostile bytes, so it must not be able to plant code that the
API or a later worker would run, or rewrite the host's working tree. `data/`
is read-only too; only `data/samples/` and `data/uploads/` under it are
writable, for the sample mirrors and the uploads. A source edit reaches a
production container only when it restarts. The development overlay (`make
dev-up`) mounts the sources writable and reloads the API on an edit.

The API, the workers and the migration run as an unprivileged account (uid and
gid 10001 by default) with every Linux capability dropped and
`no-new-privileges`. The image's virtual environment and sources are owned by
root, so that account can only read them. Set `MALSPARK_UID` and `MALSPARK_GID` in
`docker/.env` to run them under another id; on a machine where a login user
also works in this checkout's `data/`, use that user's ids (`id -u`, `id -g`)
so the files stay theirs. `make docker-up` and `make dev-up` set both to the
invoking user's ids (under `sudo`, the user who ran it) when neither the
environment nor `docker/.env` sets them, and to 10001 when that user is root.

### Volume ownership

Before the backend ran unprivileged it ran as root, so a deployment created
then has entries in `data/samples/`, `data/uploads/` and the `attck_cache`
volume owned by root. The one-shot `volume-init` service hands the
root-owned ones to `MALSPARK_UID:MALSPARK_GID` before the API and the worker
start, on every `up`:

- It never takes a file from anyone else. An entry owned by a uid or gid that
  is neither root nor the target stops it before it has changed anything, with
  the id to set, for example `volume-init: data/samples is owned by uid 1000;
  set MALSPARK_UID/MALSPARK_GID=1000 in docker/.env`. The API and the worker then
  do not start.
- It changes ownership only (`chown -h`), never a file's content or mode, never
  through a symbolic link, never past the mount it was given, and executes
  nothing it finds.
- It touches only root-owned entries, so after the first run it changes
  nothing.
- It runs as root with only the `CHOWN` and `DAC_READ_SEARCH` capabilities
  (the second lets it enter the 0700 work directories), with no network, and
  exits. It refuses a uid or gid that is 0 or not a number.

Nothing needs doing by hand: the first `docker compose up -d` after the upgrade
runs it. To run it alone, `docker compose run --rm volume-init`. The ATT&CK
cache now mounts at `/home/malspark/.cache/malspark` (the volume keeps its name),
so its contents carry over.

The worker writes its sample mirrors 0700 and 0600 as `MALSPARK_UID`. The
`ghidra-mcp` container runs as that same uid and gid, so it reads them through
its read-only mount; it shares nothing else with the worker. A Ghidra that runs
as another user needs a group it shares with the worker, and mirrors written
0750 and 0640 for that group.

### The container that opens the sample

`ghidra-mcp` opens the sample, so it is kept from the platform: it runs as
`MALSPARK_UID:MALSPARK_GID` (volume-init hands the `ghidra_projects` volume over
first), with no Linux capability, no way to gain one and a process limit
(`GHIDRA_PIDS_LIMIT`, 2048 by default). Its only secret is its own
`GHIDRA_MCP_AUTH_TOKEN`. Its one network is `ghidra`, internal (no gateway),
shared only with `backend-api` and `backend-worker`, which reach it at
`http://ghidra-mcp:8089`, and with `ghidra-port`. It publishes no port and has
no route to the internet, the host, Postgres, Redis, MinIO or Qdrant. A
deployment that points it at a shared Ghidra server elsewhere needs a network
with a route to that server. The JVM's home is `/tmp` (`JAVA_TOOL_OPTIONS`),
since the uid has none in the image.

`ghidra-port` (same `ghidra` profile) publishes Ghidra's port on `BIND_ADDRESS`
for a worker run on the host (`http://localhost:8089`): a relay that forwards
bytes to `ghidra-mcp:8089` and nothing else. It mounts nothing, holds no
variable, runs as `65534:65534` with no capability, no way to gain one and a
read-only root, and its other network, `ghidra-publish`, carries nothing else.

`GHIDRA_USER` is empty by default: the platform imports each sample without a
Ghidra project, so the name Ghidra runs as owns nothing it opens. A project in
`ghidra_projects` created while the image ran as root is owned by `root`, and
Ghidra refuses a project owned by another name; an operator who opens such
projects sets `GHIDRA_USER=root` in `docker/.env`.

The identification servers (`die-mcp`, `ilspy-mcp`, `goresym-mcp`) open the
sample too, and are held the same way: `MALSPARK_UID:MALSPARK_GID`, no capability,
no way to gain one, a process limit, and its own token as its only secret.
Each also runs with a read-only root whose only writable place is a tmpfs at
`/tmp`, mounts the samples directory read-only at `/data/samples` and nothing
else, and is on an internal network of its own (`die`, `ilspy`, `goresym`)
shared only with `backend-api`, `backend-worker` and its relay, whose other
network (`die-publish` …) carries nothing else. Each has a memory ceiling the
kernel enforces, with swap pinned to it, as Ghidra's: a machine-safety limit,
not a bound on the analysis, since a program's output is read whole. A file
past it fails its call and the run records the failure; `DIE_MEM_LIMIT`
(2g), `ILSPY_MEM_LIMIT` (4g) and `GORESYM_MEM_LIMIT` (2g) in `docker/.env`
change them.

The rule and document servers (`yarax-mcp`, `oletools-mcp`, `webcrack-mcp`)
are held exactly so, on networks of their own (`yarax`, `oletools`,
`webcrack`) with their relays' (`yarax-publish` …), with 2g each
(`YARAX_MEM_LIMIT`, `OLETOOLS_MEM_LIMIT`, `WEBCRACK_MEM_LIMIT`). `yarax-mcp`
mounts one directory besides the samples, the operator's YARA rule files,
read-only at `/data/rules`.

The container and Android servers (`unblob-mcp`, `jadx-mcp`) are held exactly
so, on networks of their own (`unblob`, `jadx`) with their relays'
(`unblob-publish`, `jadx-publish`), with 2g and 4g (`UNBLOB_MEM_LIMIT`,
`JADX_MEM_LIMIT`), and each has a `/tmp` of its own, a tmpfs sized below that
ceiling (`UNBLOB_TMPFS_SIZE`, `JADX_TMPFS_SIZE`, 1536m each), so a run that
writes too much fills the file system rather than the container's memory.
Keep each below its memory ceiling and change the two together: unblob's at
about three quarters of `UNBLOB_MEM_LIMIT`, JADX's at `JADX_MEM_LIMIT` less its
heap (half of it) and about 0.5 GiB more for the runtime.
`unblob-mcp` writes the files it extracts under `/tmp/carved`; it stops a run
past the larger of the sample's size and `UPLOAD_MAX_BYTES` (100 MiB unless
set; set it to the console's `upload_max_bytes` where you raised that) or past
`UNBLOB_MAX_ENTRIES` entries (100000 unless set), no one file it writes may
pass that byte bound, and it removes each extraction `CARVED_KEEP_SECONDS`
after it was written (3600 unless set), the oldest first when a new run would
not fit.

## Where a tool server sees the sample

The worker copies each sample into a directory under `data/samples/` on the
host, one per server that needs a copy (`.work` by default), and a
containerised server mounts `../data/samples` inside its own container. Each
server's block declares that mount as its `sample_mount`; the worker hands the
server its copy under it. Ghidra's ships `/data/samples`, the mount the
`ghidra-mcp` service writes (read-only), whether or not the worker itself runs
in Compose. A server on the worker's own filesystem (a stdio sidecar) declares
none and is handed the host path. See [What a server declares about its
tools](/docs/configuration/#what-a-server-declares-about-its-tools).

Set to a path the container does not have, Ghidra answers every load with
`File not found: ...`, the Ghidra agent stops before its first model turn with
"Ghidra could not open the job's sample: ...; check
core.static.ghidra.sample_mount / the container mount", and the rest of the
team runs without it. The worker's first lines say, for each static provider
the settings select, where its copy goes and the path its server is handed:

```text
Static provider 'ghidra' mirrors a sample to data/samples/.work/<sha256> and is handed it as /data/samples/.work/<sha256>.
```

`GHIDRA_CONTAINER_SAMPLES_PATH` is retired. The migration that retired it read
a value other than `/data/samples` once into `core.static.ghidra.sample_mount`,
where the store held none; a worker that still has it set warns at start and
names that setting. `MALSPARK_ATTCK_MAX_AGE_DAYS` is retired the same way: a
whole number other than 7 is read once into `core.validation.attck_refresh_days`
(0 or less as 0, never check), which the console edits under Analysis layers →
ATT&CK data. The revision reads the environment of the process that runs it; in
compose that is the `migrate` service, which is handed the variable from
`docker/.env`.

## Rotating the JWT signing secret

Three steps and one wait. The wait is the part a rotation is usually forgotten
in, so the end of it is something you write down.

1. Move the current `JWT_SECRET_KEY` to `JWT_PREVIOUS_SECRET_KEY` and
   `JWT_KEY_ID` to `JWT_PREVIOUS_KEY_ID`, put the new secret in
   `JWT_SECRET_KEY` and a new id in `JWT_KEY_ID`, and set
   `JWT_PREVIOUS_SECRET_NOT_AFTER` to the moment the old secret stops being
   accepted — an ISO-8601 timestamp, read as UTC when it carries no offset.
   Make it a little longer than the refresh-token lifetime
   (`jwt_refresh_token_expire_days`), because that is the oldest token still in
   circulation. Restart the API and the worker. The moment is optional and a
   previous secret without one is accepted with no end — the startup check
   warns about that at every start until you set it or clear the previous
   secret — but a value that does not read as an ISO-8601 moment is refused at
   startup rather than taken as "no end".
2. Wait. New tokens are signed with the new secret and carry the new `kid`;
   tokens already issued keep working until they expire. `GET
   /api/v1/system/status` reports the rotation to an admin caller under
   `jwt_grace_secret` — the previous `kid`, when it lapses, whether it is still
   accepted and whether an end was written down at all (`bounded`) — and the
   API logs the same line at every start.
3. After the moment passes, a token signed with the old secret is refused and
   `jwt_grace_secret.accepted` reads false; the startup check then warns until
   you clear `JWT_PREVIOUS_SECRET_KEY` and `JWT_PREVIOUS_SECRET_NOT_AFTER`.

Nothing rotates on its own. The point of the timestamp is that a secret you
forget stops being honoured rather than being honoured for the life of the
deployment. See [Security](/docs/security/) for where signing sits among the
rest of the auth posture.

## Outside Compose

The API and the worker need nothing but the bootstrap contract in their process
environment, so any orchestrator that can inject environment variables can run
them.

- **API**: `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` from the
  repository root, without `--reload`.
- **Worker**: `uv run arq app.worker.analysis_worker.WorkerSettings`.
- **Kubernetes**: put the contract in a Secret and a ConfigMap and inject it as
  environment variables. `SETTINGS_ENCRYPTION_KEY` must be identical for the
  API and the worker deployments, or the worker cannot open the credentials the
  console stored. Point the liveness probe at `/healthz` and the readiness
  probe at `/health?deep=true`. Run migrations as a Job before the rollout and
  leave `RUN_MIGRATIONS_ON_STARTUP` false, so replicas do not race the same
  upgrade.
- **systemd**: an `EnvironmentFile=` pointing at a root-owned copy of
  `bootstrap.env` is enough for both units; nothing else is read from disk.

Behind a reverse proxy, set `CORS_ORIGINS` to the console's real origin, keep
`COOKIE_SECURE` true, and populate the `trusted_proxy_ips` setting so the rate
limiter honours `X-Forwarded-For` only from your proxy.

## VirusTotal over stdio (optional)

The `virustotal` built-in needs nothing installed: it is VirusTotal's own
server over HTTP, and registering an agent token from Settings → Setup guides
is the whole setup. Install the package only for `submit_local_file`, the
upload-by-path tool that exists solely when the server runs on the host that
holds the sample:

```bash
uv tool install --python 3.12 vt-mcp==0.8.4
```

`uvx --python 3.12 vt-mcp==0.8.4` runs the same release without installing it.
The command is stdio-only and takes no flags; it reads the agent token from
`VTAI_TOKEN` (or `VTAI_TOKEN_FILE`) in its own environment. Add it as a second
tool server with transport `stdio` and put the variable name in `env_allow`, so
the token reaches the child from the worker's environment rather than being
written into a setting the console echoes back.

A server added this way is started with exactly the names it lists. A built-in
is the one case where that field has a floor: `analysis` and `network` are
always passed the sample roots and the staging directory, whatever the stored
registry holds, because a child without them refuses the run's own sample. See
[Configuration](/docs/configuration/#which-directories-a-sidecar-may-read).
