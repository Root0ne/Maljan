## What was measured

The question is simple: when Malspark analyses a sample on its own, how much of
what expert human analysts published does it find, does it get anything wrong,
and what does it find that they did not write down?

### The sample

The reference sample is a {run.sample} bot DLL, sha256
<code>{run.sha256}</code>.
[Bitsight, *Latrodectus, are you coming back?* (João Batista, 2024-06-17)](https://www.bitsight.com/blog/latrodectus-are-you-coming-back)
lists this hash among the samples it analysed.

### The key: K1 to K11

The key is a list of facts drawn from three public human analyses of the
family: Bitsight's report above, and the analyses Elastic and Proofpoint
published. The facts are sorted into eleven groups:

- **K1 to K10** hold the {run.items} scored facts: identity, execution flow,
  anti-analysis, identifiers, persistence, command and control, commands,
  discovery, indicators and ATT&CK techniques.
- **K11** holds the human reports' detection content: their YARA, Suricata and
  Sigma rules and hunting advice. It is not scored. It is used only to decide
  what counts as beyond the human reports.

Build-specific values, such as the C2 domains, the group name and the RC4 key,
are checked for consistency with the human reports, which describe the family
across many builds.

### How a fact is scored

Each of the {run.items} facts gets one verdict:

| Verdict | Meaning |
| :-- | :-- |
| Found | The report body states the fact, with its purpose right. |
| Partly | The report body states part of the fact, or states it with the wrong purpose. |
| Partly, from the evidence bundle | The fact appears only in the evidence bundle that ships beside the report, bound to the routine it comes from, and not in the report body. |
| Missed | The report does not state the fact. A string that only hints at a behaviour counts as missed. |
| Wrong | The report states the fact in a way the human reports contradict. |

The scorer checks every verdict against the run's stored evidence ledger, not
only against the report text.

### Beyond the human reports

A fact counts as **beyond human** when all three hold:

1. The report body states it.
2. No item of K1 to K11 holds it, and no human report states it for this hash.
3. The run's own ledger proves it: a tool answer, a decoded string, a sandbox
   record or a decompile, cited by its `ev_` id.

A wrong claim, or one the evidence does not prove, is never counted. It is
listed separately and left out of the total.

### Keeping the run honest

- **The run is blind to the key.** The human reports are not given to the
  agents, and the run starts on {run.memory}, so nothing learnt from an earlier
  run of the same sample reaches it.
- **Nothing is tuned for the sample.** The team and its prompts are the
  importable [all-tools team](/examples/profiles/all-tools.json), unchanged;
  the model, effort and sandbox are the ones listed under Setup, and nothing
  was set for this sample.
- **Blind A/B scoring is available.** When two runs are compared, the
  [blind scoring](/docs/blind-scoring/) tool hides which report came from which
  run until the scorer has finished. This page scores a single run, so it has
  no arm to hide.

## Limitations

- **One sample, one run.** No variance is measured. A rerun can move a
  borderline fact between found and partly.
- **One scorer.** The project scores its own runs. Every verdict quotes the
  report sentence it rests on and is checked against the ledger, but the
  scorer knows which run it is reading.
- **A family well described in public.** The reference reports exist because
  the family is well known. A new family has no key to score against.

## Reproducing the run

<Steps>

<Step>

Start a stack and connect the model and the sandbox, as in the
[quick start](/docs/getting-started/).

</Step>

<Step>

Import the [all-tools team](/examples/profiles/all-tools.json) and give it
the servers and providers it names, as [An all-tools
team](/docs/configuration/#an-all-tools-team) describes.

</Step>

<Step>

Upload the sample and submit a job that ignores earlier runs, on a stack
whose long-term memory is empty:

```json
{
  "sample_id": "<the sample's id>",
  "config": {"profile": "all_tools", "ignore_earlier_runs": true}
}
```

</Step>

<Step>

Score the stored report against the key, fact by fact, and check each verdict
against the ledger (`GET /api/v1/jobs/{job_id}/evidence`).

</Step>

</Steps>
