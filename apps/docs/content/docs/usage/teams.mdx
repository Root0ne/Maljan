An **agent** is a model with a prompt, a role and a set of tools. A **team** is
an ordered list of **stages**, and each stage runs the agents it names. Both
are configuration: you write them in the console, export them as JSON and
import them elsewhere. No code change is needed.

## Agents

Nine agent definitions ship built in:

| Agent | Role | What it does |
| :-- | :-- | :-- |
| `triage` | `generic` | Reads the pack's facts first and decides what the rest of the team should look at. |
| `static` | `static` | Reads the file through the static provider and the analysis tools. |
| `reverser` | `generic` | Takes each static finding into the decompiler and confirms or refutes it at function level. |
| `android_static` | `generic` | Reads an APK or DEX file. |
| `dynamic` | `dynamic` | Reads the sandbox report: processes, files, registry, signatures. |
| `network` | `network` | Reads the capture and the sandbox's network record. |
| `lead` | `lead` | Plans the analysis and asks the other agents through `ask_<agent>` tools. |
| `judge` | `judge` | Mediates the debate and states the verdict. See [Debate and judge](/docs/concepts/debate-and-judge/). |
| `reporter` | `reporter` | Writes the report. See [Report](/docs/concepts/report/). |

`static`, `dynamic`, `network`, `judge` and `reporter` have a class behind
them. The other four are a prompt and a tool list, nothing else. A definition
of your own is the same: a prompt, a role, a model if it should differ from
the global one, and its tools.

An agent's tools are references:

| Reference | Gives the agent |
| :-- | :-- |
| `{"kind": "mcp", "server": "<key>"}` | Every exposed tool of that MCP server. |
| `{"kind": "provider"}` | The tools of the static provider the agent opens. Only on a `generic` or `lead` agent. |
| `{"kind": "sandbox"}` | Tools over the job's sandbox report. |
| `{"kind": "agent", "agent": "<key>"}` | An `ask_<key>` tool that hands a task to another agent. |
| `{"kind": "capability", "capability": "reputation"}` | Every built-in server that serves that kind of tool. |

The agent decides which tools to call, in what order and when to stop. Every
call goes to the [evidence ledger](/docs/concepts/ledger/).

## A team, written out

This is an abridged excerpt of the importable [all-tools team](/examples/profiles/all-tools.json)
(the `all_tools_qu1cksc0pe` definition and the reverser's full prompt are left out),
which the [benchmark](/docs/benchmark/) runs. It adds a radare2 analyst and a
Ghidra reverser to the built-in agents:

```json
{
  "format": "malspark-settings/1",
  "values": {
    "core.agents.definitions": {
      "all_tools_static_r2": {
        "role": "static",
        "label": "Static analyst (radare2)",
        "category": "code_reader",
        "static_provider": "r2",
        "tools": [{"kind": "mcp", "server": "analysis"}, {"kind": "mcp", "server": "knowledge"}]
      },
      "all_tools_reverser_ghidra": {
        "role": "generic",
        "label": "Reverser (Ghidra)",
        "category": "code_reader",
        "prompt": "You are the reversing step of a malware-analysis team. ...",
        "static_provider": "ghidra",
        "tools": [{"kind": "provider"}, {"kind": "mcp", "server": "knowledge"}, {"kind": "mcp", "server": "virustotal"}]
      }
    },
    "core.agents.profiles": {
      "all_tools": {
        "label": "All tools",
        "stages": [
          {"key": "triage_pack", "label": "Triage pack", "kind": "triage", "inject_upstream": "none"},
          {"key": "triage", "label": "Triage", "kind": "analysis", "agents": ["triage"], "inject_upstream": "none"},
          {"key": "static", "label": "Static", "kind": "analysis",
           "agents": ["static", "all_tools_static_r2", "all_tools_qu1cksc0pe"],
           "depends_on": ["triage"], "inject_upstream": "findings"},
          {"key": "reversing", "label": "Reversing", "kind": "analysis",
           "agents": ["all_tools_reverser_ghidra"], "depends_on": ["static"], "inject_upstream": "findings"},
          {"key": "dynamic", "label": "Detonation", "kind": "analysis", "agents": ["dynamic"],
           "depends_on": ["static", "reversing"], "when": "has_sandbox_report", "inject_upstream": "findings"},
          {"key": "network", "label": "Network", "kind": "analysis", "agents": ["network"],
           "depends_on": ["static", "reversing", "dynamic"], "when": "has_pcap or has_sandbox_report",
           "inject_upstream": "findings"},
          {"key": "debate", "label": "Debate", "kind": "debate", "depends_on": ["network"]},
          {"key": "verdict", "label": "Verdict", "kind": "verdict", "agents": ["judge"], "depends_on": ["debate"]},
          {"key": "report", "label": "Report", "kind": "report", "agents": ["reporter"], "depends_on": ["verdict"]}
        ]
      }
    }
  }
}
```

Read it top to bottom: the pack, then triage, then three static analysts at
once, then the reverser with their findings, then detonation if there is a
sandbox report, then the network pass, the debate, the verdict and the
report. How to import it, and the servers it needs, is in [An all-tools
team](/docs/configuration/#an-all-tools-team).

A team is stored under `core.agents.profiles.<key>` and edited under
**Settings → Configuration → Agents and pipeline → Teams**. The complete field
reference is [Teams and stages](/docs/configuration/#teams-and-stages); the
runtime view is [Agents and teams](/docs/architecture/#agents-and-teams).

## The teams that ship

| Team | Stages | For |
| :-- | :-- | :-- |
| `default` | `triage_pack` → `analysis` (static, dynamic, network) → `debate` → `verdict` → `report` | The general case: three analysts, with the pack in front of them. |
| `measurement` | The same four model stages, without the pack and with every tool server withheld | What the ensemble contributes on its own, with nothing to call. |
| `mobile` | `triage_pack` → `triage` → `android_static` → `dynamic` → `debate` → `verdict` → `report` | An APK or a DEX. The Android stage declines on anything else and says so. |
| `deep_static` | `triage_pack` → `triage` → `static` → `reversing` → `network` → `debate` → `verdict` → `report` | Reading the code: the reversing stage takes each static finding into the decompiler. |
| `team_lead` | `triage_pack` → `lead` → `verdict` → `report` | One lead agent plans, asks the specialists through `ask_<agent>` tools, and reports what they established. |

`triage_pack` is the deterministic pre-analysis pack, which runs no model; the
`triage` stage after it is the triage *agent*.

## Picking a team

<Tabs items={["For the deployment", "For one job"]}>

<Tab value="For the deployment">

Make it the active team under **Settings → Configuration → Agents and pipeline → Teams**
(`core.agents.profile`).

</Tab>

<Tab value="For one job">

Name it on the job:

```bash
curl -X POST http://localhost:8000/api/v1/jobs \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"sample_id":"<id>","config":{"profile":"measurement"}}'
```

</Tab>

## What a stage is

| Field | Meaning |
|---|---|
| `key` | Slug, unique in the team. Names the stage everywhere it is reported. |
| `kind` | `triage`, `analysis`, `debate`, `verdict` or `report`. |
| `agents` | The agent definitions the stage runs. |
| `depends_on` | Earlier stages this one runs after. |
| `when` | The condition deciding whether it runs. Empty means always. |
| `mode` | `parallel` or `sequential`, for an analysis stage; unset, it follows the job's analyst mode. |
| `inject_upstream` | `none`, `findings` or `full`: what the stage is told about the stages it depends on. |
| `builtin_tools` | `false` withholds every built-in tool server from this stage's agents. |

The full table, with labels and debate options, is in
[Teams and stages](/docs/configuration/#teams-and-stages).

## Conditions

`when` is a small expression language — Python's grammar with an allow-list on
top — over the sample and the run so far:

```
platform == "windows"
extension in ("apk", "dex")
has_pcap and stages.triage.claim_count > 0
"T1055" in stages.static.technique_ids
triage.rule_hits > 0
triage.hits["signature_rules"] > 0
```

A condition that does not parse is refused when the team is saved, and the
console checks each condition box as it loses focus. One that fails at run time
skips its stage with the reason recorded rather than failing the job. Every
name the language knows is listed in [Conditions](/docs/configuration/#conditions).

## The measurement baseline

`measurement` is the same analysts as `default` with every tool server withheld
(`exclude_servers: ["*"]`), the in-process sandbox tools withheld and the static
provider forced to `none`. Running the same sample under both teams answers a
question the default team cannot: how much of the verdict was the tools and how
much was the model. Compare its verdict, its techniques and its
`run_summary.corroboration` against the default run.

<Callout type="idea" title="Why a wildcard">

A fixed list of the built-in server keys would still hand the baseline any
server an operator added afterwards. See [Tools, and the measurement
baseline](/docs/configuration/#tools-and-the-measurement-baseline).

</Callout>

## Writing a team of your own

Built-in teams are editable only in their debate options, their
`builtin_tools` switches and `exclude_servers`; everything else means cloning
the team, which the console does in one click.

- **Generic agents.** `triage`, `android_static` and `reverser` are seeded
  generic definitions: a prompt and a tool list, no class. Clone one as the
  starting point for an agent of your own.
- **A prompt that names a tool the agent no longer has.** When an agent's own
  prompt spells, exactly as declared, the name of a tool the platform knows
  (any configured server's, or a shipped declaration's) that the agent's tool
  set lacks, the settings answer carries a warning under
  `core.agents.definitions.<agent>`, the job logs one WARNING line naming the
  agent and the tools. The run summary has no advisory channel, so the run is
  not marked degraded for it. A plain word such as `strings` counts only inside
  backticks or quotes; a name with `_`, `.`, `-` or a digit counts anywhere. It
  never refuses a save or a run, and built-in prompts are not checked.
- **Checked as you type.** The team editor sends the staged teams to
  `POST /api/v1/settings/lint-teams` and draws each team's stage graph with
  its findings beside it. See [Checking a team before it is
  saved](/docs/configuration/#checking-a-team-before-it-is-saved).
- **Delegation.** An agent can ask another agent for work the way it calls a
  tool: `ToolRef(kind="agent", agent="static")` puts `ask_static` in its
  toolbox. See [Delegation](/docs/configuration/#delegation).
- **An all-tools team to import.** `docs/examples/profiles/all-tools.json` runs
  three static analysts on three tools, a Ghidra reverser, and the dynamic and
  network stages. See [An all-tools team](/docs/configuration/#an-all-tools-team)
  for the import and what it needs.

## How the analysts of a stage run

`core.llm.parallel_analysts` is `auto` (the default), `true` or `false`. Under
`auto` the job decides from the endpoints its models are served at: a hosted
API runs the analysts in parallel, while Ollama or a local server with one slot
runs them one after another, because concurrent analysts on a single-slot
server clobber each other's state. A stage whose own `mode` is set keeps it.
The rule in full is in [How an analysis stage runs its
agents](/docs/configuration/#how-an-analysis-stage-runs-its-agents).
