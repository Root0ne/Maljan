## What Malspark does

Malspark runs the whole analysis without a human in the loop:

1. **Code establishes the facts first.** The triage pack identifies the file,
   hashes it, checks its signature, runs the rule engines and decodes its
   strings. No model is involved.
2. **Analyst agents investigate.** Each analyst uses real tools: a decompiler,
   a disassembler, a sandbox, capture readers, reputation services. The agent
   decides what to call and when to stop.
3. **The analysts argue.** A mediator puts their claims side by side and lists
   every contradiction. The analysts it names must revise, with the evidence in
   front of them.
4. **A judge decides.** The judge states the verdict, the family and the
   ATT&CK techniques, and drops what the evidence does not support.
5. **The report cites everything.** Every tool call is written to the evidence
   ledger with an id such as `ev_0021`. Every report section names the ids it
   rests on.

## Why it is built this way

- **The agent decides; the code checks.** Nothing rewrites a claim, a
  technique id or a confidence behind an agent's back. When a claim breaks a
  rule, the code tells the agent why, with a [validation
  code](/docs/concepts/validation/), and the agent gets a turn to fix it. What
  it will not fix stays on the record.
- **Evidence or it did not happen.** A claim that cites no ledger entry, or an
  entry that does not hold what the claim says, is flagged. A reader can open
  every citation and see the call, its arguments and its answer.
- **Any tool, any model.** Teams, tools, models and sandboxes are
  configuration. An MCP server Malspark has never seen is used at full
  strength. See [Bring your own tools](/docs/tools/).
- **Any format.** The sample's own bytes decide its route: PE, ELF, Mach-O,
  APK, DEX, documents, scripts, archives. A format nothing recognises still
  gets an analysis, and the report says so.

## What you get

| Output | Where |
| :-- | :-- |
| The report, as Markdown, HTML and PDF | The console, or `GET /api/v1/reports/{report_id}/markdown` |
| A STIX 2.1 bundle | `GET /api/v1/reports/{report_id}/stix` |
| An ATT&CK Navigator layer | `GET /api/v1/reports/{report_id}/attack-layer` |
| An IOC feed with a publish decision on every row | `GET /api/v1/reports/{report_id}/iocs` |
| Detection drafts: YARA, Suricata, Sigma | In the report's Detection section |
| The evidence bundle and the sealed ledger | `GET /api/v1/reports/{report_id}/evidence-bundle.html` |

See [Reports and exports](/docs/usage/reports-and-exports/).

## How well it works

The latest benchmark run analysed a Latrodectus sample with a hosted model. It
recovered 56 of 57 facts from public human reports, got none wrong, and stated
58 verified facts those reports do not hold. See [Benchmark](/docs/benchmark/).

<Callout type="warn" title="Analyse malware only in isolated, authorised environments">

Malspark handles live malware. Run it, and any sandbox it submits to, only on
hosts and networks you are authorised to use for that purpose, isolated from
production systems and data. A sandbox detonates the sample; the mock sandbox,
the default, executes nothing. Uploading a sample to an external service such
as VirusTotal publishes it; that tool ships switched off. See
[Security](/docs/security/#handling-samples).

</Callout>
