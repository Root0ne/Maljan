### Changed

- **The repeat guard is a stated stall limit, and the judge's asks run at once on a hosted API (T-415e).** A tool loop used to end after three repeats of any kind, a served second call included, so a model that re-read three different answers once each was ended with nothing refused. It now ends only after eight refused calls (`RepeatGuard.ENDS_AT`), each identical in tool and arguments, as the guard's key normalises them, to a call already answered; a served retry and a call that differs in any argument or page never count. Eight is a stall limit, not a measured optimum: no stored run has a single refusal by the guard, so none comes near it, and it still ends both live loops the guard was written from (one `pe_info` call repeated through 16 of 19 steps, 11 identical `strings` calls, nine of them refused). Every refusal now names the ledger id that holds the answer and says how to read it again and page through it (`read_evidence` with `evidence_id`, `offset` and `limit`), and a refused re-read of the ledger outside a loop names the id and the paging too. The judge's `ask_*` calls in one turn, as mediator or verdict, run at once where the asked agents' models serve concurrent requests: an asked analyst as the job's analyst run mode reads it (`llm.parallel_analysts`, else each provider's declared concurrency and a local server's `/props` slots), an asked agent in no stage by that rule over its own models whatever the setting says; on a local single-slot server they run one after the other, as before, and the ask tool's description reads as it did. The answers come back in the order of the calls and the asked agents' ledger entries are merged in ledger-id order, however the asks finish. A lead's asks stay serial.
