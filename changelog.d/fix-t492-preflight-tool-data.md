### Fixed

- **A tool whose rules are missing is named before the job, not only in its degraded block (T-492).** A run was accepted with nothing named unavailable and then lost capa: its library was installed, but its rules directory, which is fetched rather than tracked, had never been fetched into the run's worktree, and the check before a job looked only at libraries and executables. A tool's declared needs may now include a data path (`capabilities.data`: its default path, the setting a caller that reads it hands the tool instead, the server variable that overrides the default, the file pattern a directory must hold), and `POST /jobs` and the system status name a tool whose declared path is missing, an empty file or a directory holding no matching file, looked at where the tool reads it (a server's tool its override or default, the worker's own reading the setting), with what named the path, the path relative to the project root (one outside it is not shown) and how to put it there. The built-in sidecars declare capa's rules (`static.capa.rules_dir`) and the Sigma corpus (`MALJAN_SIGMA_RULES_DIR`, else `data/sigma_rules`), the two corpora a fresh clone or worktree lacks until `make external` has run. It is a warning, as for a missing library; a server's own manifest does not probe the path, a server block that sets `PYTHONPATH` has its data unchecked as its modules are, and a tool that declares no data is checked as before, so no run changes.
