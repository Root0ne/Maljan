### Changed

- **Leftover tool-name literals are read from declarations, declared kinds and their implementations (T-418, T-426).** Which names in an analyst's claim are code locations (the report's claims not discussed) is no longer a pattern of five prefixes written in the report code: it is built from the prefixes every enabled source declares before an address, for a function (`auto_name_prefixes`) and, through a new server-level declaration field, `data_label_prefixes`, for a datum, together with the prefixes the platform has always read (`FUN_`, `fcn.`, `sub_`, `func.`, `loc.`, `LAB_`, `SUB_`, `sub.` and `DAT_`, which the Ghidra block now also declares as its data-label prefix), each with its own separator and in either case. A server nobody shipped whose decompiler writes its own prefixes has its claims read as a built-in one's; a data-label prefix is never read as a function's name. A stored entry's API hash resolution, written before entries recorded their source, is the platform's own when the source its server names (the triage pack's, or the tool server of that key) declares `platform_owned`, instead of when its server is one of two names. Whether a triage-pack answer that says `reason` beside its rows established anything is read by the kind the entry stores (`function_matches`, `api_catalogue`), not by the tool's name, and the pack's own step that measures its peak memory is found by its in-process implementation, not by its id. The reading of an anti-analysis scan's rows and the rule they are stated by sit in `analysis.anti_analysis`, so a server's declared scan no longer imports Ghidra's module, and CAPE's guest platform names sit in the CAPE adapter rather than in the shared sandbox helpers. Every stored run replays as before.
