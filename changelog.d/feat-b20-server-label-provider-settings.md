### Added

- **A tool server is named by its label, and a third-party provider's block has a place in the settings (G14).** A reputation lookup whose facts name no service nor display name is attributed to its tool server's `label` when the entry is written (then to its key, as before); a declared `service` or `display_name` still comes first, and a stored record keeps the name it recorded. A rest's record, its `tool_server_rested` event and `run_summary.server_rests` carry the server's `label` beside its key where the label is not the key, and the sentence the report and the console print names it `Label (key)`. The roster (event and `GET /api/v1/jobs/{id}`) carries `servers`, each tool server's label by its key where it is not the key, and a server's own tab in the console is drawn under it; the key stays the id everywhere (routes, the ledger, events, the tool-call rows). A server with no label of its own reads exactly as before. `core.providers` holds one server block per third-party provider, keyed by its id (Settings → Plugins, a JSON editor): its tools are declared under `provider:<id>` from that block with no code naming the provider, before the class's `declaration(cfg)` hook, the run's snapshot records it like a built-in's block, `tool_declarations.provider_block(settings, id)` reads it, and a class may name `providers.<id>` as its `declaration_block` (another entry, the map itself and a tool server's block in `mcp.servers` are refused at registration). A block validates as a tool server's entry; a provider id that is not one, a built-in provider's id, a renamed spelling and a strict-rule break in a changed tool declaration are refused on save at `core.providers.<id>`, and since the map is one clear row a block holds no token, no `env` value, no URL with a user name or password and no credential bootstrap (a credential goes by name through `env_allow`). An entry for a provider whose class registered another block is not read (logged once) and is refused on save. Empty by default; stored settings read as before and need no migration. The validation harness's scenario e names the stub by its label again on the proposed variant. T-124, T-130 and T-133 of this batch were already on dev (#417).
