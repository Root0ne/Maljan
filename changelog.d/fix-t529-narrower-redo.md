### Fixed

- **A narrower call is no redo of a failed one (T-529).** A failed call counted as redone (T-494 D6) when a later call of the same tool asked the same question with any argument absent or null on either side, or with the value the failure's message named replaced by any other, so a redo that asked less counted: the whole routine asked and three instructions of it answered, or a read of 0x1000 bytes refused and a read of 4 answered. A redo is now never narrower than the failed call. An argument the failed call left absent or null and the redo sets counts only where the tool's declared default for it is known and is that value; the ledger carries no tool's input schema, so such a call is no redo. A refused value the redo replaces by a number counts only when that number, decimal or `0x` hex, is not smaller than the refused one. An argument the redo leaves absent or null, and a refused value replaced by a value that is no number, read as before. Every failed call is still counted and listed as failed; only the redone list is narrower. Offline, over the stored ledgers of run7, run5, run4, local8, haiku4, haiku5, haiku7 and haiku8: 9 of the 17 failed calls read as redone no longer are, 3 in run7 (decompiles redone by a decompile of another server that set `timeout` 120) and 6 in haiku5 (two decompiles redone with `timeout` 120 and four cross-reference lists redone with `limit` 50 and `offset` 0, after the tool refused the null each failed call sent); haiku7's 2 and haiku8's 3 redone calls stand.
