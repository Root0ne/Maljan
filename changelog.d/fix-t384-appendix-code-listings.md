### Fixed

- **The evidence appendix draws each function's code whole, as a listing, instead of cutting it into a table cell.** Appendix A cut every table cell at 160 characters, so a batch of decompiled functions printed each body as its first line and an ellipsis in the Markdown, the HTML and the PDF, though the report held it. A value that is code — a value of more than one line in a section whose cited entry declares decompiled or disassembled code, or one that names the function its row names — is now drawn as a fenced listing under the section's table, headed by its number, the function's address and name and, where the section cites one entry, that entry; the table cell points to the listing. What is code is read from the declared kind and the content, never from a tool's name. A one-line value is still cut to fit the page at 160 characters (an item at 200), and a section with a value cut now says under it where the value is whole: its entry, the entries cited under it, or the JSON report's section. A listing the report was built with cut says so and where it is whole. The methodology appendix says that code is never cut to fit the page.
- The surface checker holds code to the same rule: a section value the renderer draws as a listing must be on the Markdown and the HTML whole, and a cut of it is a truncation defect rather than a declared cut (`checked.section_code` counts them).
- What stays as it was: the report body, the JSON report, the STIX export and every other surface are unchanged; a report is larger by its listings (haiku6: 670 to 703 KB of Markdown, 365 to 390 PDF pages). The report build still cuts a stored table value at 400 characters, so a long function a stored report holds ends in the cut mark in its listing, which points to the evidence ledger.
