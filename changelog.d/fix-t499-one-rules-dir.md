### Fixed

- **Every reading of capa reads the rules directory the operator configured (T-499).** `static.capa.rules_dir` was honoured by the worker's own reading of capa and by the static provider, while the analysis server's `capa` tool always read `data/capa-rules`: a setting pointed elsewhere gave a run two rule sets, and an agent's capa call failed where only the configured directory existed. A tool's data declaration that names both a core setting and a server variable (`capabilities.data(..., setting=, override=)`) now has the setting's value handed to a sidecar of this repository under that variable when it is launched over stdio, when the setting names a path other than the default (handed as an absolute path, so a server started elsewhere reads the same directory); an empty rules directory handed to capa names no path rather than being read as the project root; capa's rules declare `MALJAN_CAPA_RULES_DIR`, which the server's `capa` tool reads. `POST /jobs` and the system status look at the handed path for the server's tool, so the readiness answer and the run agree. A block whose `env` sets the variable keeps its value, a server reached at an address or run as another program keeps its own environment, a tool declaring no such data is unaffected, and under the default no launch changes, so stored runs are unchanged.
