### Fixed

- **A rule engine that loaded no rule did not run, and says so (T-556).** Three runs scanned the sandbox report's events with no Sigma corpus (it is fetched rather than tracked, and the run's worktree had none): the worker logged a warning, the entry held `rule_count 0`, the report said "Sigma (0 hits)", the run was not degraded, and the check before the job named nothing. Sigma, YARA and capa now answer a corpus that loaded no rule as a failure with the `missing_dependency` code and the declared data path's remedy, a path outside the project named by what named it, never as the host's path. The triage pack records the step failed, the run is degraded, the header names the tool, and the run summary keeps each tool the run went without with why (`lost_tools`), which the report's scope (§2) says, escaped and with host paths masked; a summary stored before it renders as it did. The capa_yara provider says the same of missing capa rules, and the run is degraded. `POST /jobs` and the system status now also look at every enabled in-process pack step that no reading stands in for and whose tool a sidecar declares, in the worker's environment, whatever the server's block says, and name it under `pipeline`; the YARA corpus is declared too, `MALJAN_YARA_RULES_DIR` may name a directory of rule files (compiled once; a file that cannot be read is skipped and named), and a corpus that loaded nothing is read again only when it changes. A tool missing its data no longer says what it "still answers".
- **The backend image carries the Sigma corpus.** A `sigma-data` stage fetches SigmaHQ's tag that `make external` clones, checked by its sha256, into `data/sigma_rules`; a test holds the two pins together. The shipped compose file mounts the checkout's `data/` over the image's, so `make docker-up` names each fetched corpus still missing and the docs say to run `make external` first.
