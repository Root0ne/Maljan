### Fixed

- **A sandbox file, digest, key or mutex is published only as an indicator the judge names, attributed by the sample's own lineage, and the judge is asked about one whose record names no process of the sample's tree (T-355).** The guest writes temporary files, zone keys and mutexes under the sample's own processes as under every other, so the sandbox's record alone marks nothing: a host row the sandbox recorded is now published to the IOC table, `/iocs`, STIX and MISP only when the judge's indicator names it, and a row it does not name reads "the sandbox recorded it, and a file, digest, key or mutex the sandbox recorded is published only as an indicator the judge names", whatever the verdict. Which processes are the sample's is read from the same two lineage facts the network block's flows are attributed by: the processes that run the submitted file (its name or its digest) and the processes the sandbox marks as the sample's (`ProcessNode.marked`, carried by `sandbox_processes`), each with its descendants; where both facts name processes, a process in only one tree is disputed. A listed root that is neither is not the sample's, an injected process included, and a record naming a pid the facts disagree about, or a pid more than one listed process carries with different lineages, is unattributed. The sandbox tools carry the pids the report keeps, for any provider whose output has them: `sandbox_dropped_files` a file's writers (`pids`, `pid` or `process_id`, a comma-joined field split), `sandbox_registry_ops` the pids of the calls behind each key's operation, and `sandbox_mutexes` the pids of the calls that created each mutex (`pids`, by name), a create the call says found the mutex already there (`STATUS_OBJECT_NAME_EXISTS`, `ERROR_ALREADY_EXISTS`), an open and a failed create naming none. The dynamic block keeps them (`file_operations` rows, `RegistryMod.pids`, each left out of the dump when empty). A judge-named row of the sample's tree publishes with no question ("kept as an indicator by the judge's indicator; the sandbox recorded it from the sample's process tree"). A judge-named row whose record names no process of the tree is asked once, in the record's words ("the sandbox's record of it names no process of the sample's tree. Keep the indicator only if an entry of this run shows a process of the sample's tree made it, and cite that entry"), and publishes only on the keep after that question: the judge's question used to carry network facts only, so such a keep was never asked and never published. The verdict node reads the dynamic block, the run's persistence and the routed identity beside the network block, from the same repeat-free ledger the report builder reads, and `stix_renderer.sandbox_facts_for_the_judge` builds its lookups once. Only a value the rule could publish is asked about, and a Run key a persistence mechanism names is that mechanism's row and is not asked about. A provider whose output carries no pid keeps the question. Over the stored runs no host row carries a pid and no judge indicator names one, so no question is added, the network questions are unchanged, and they replay and render byte-identical; the CAPE tool goldens gain the dropped files' pids.
