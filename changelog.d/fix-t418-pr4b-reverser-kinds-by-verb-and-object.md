### Changed

- **A reverser tool's kind is read from its verb and its object; the platform ships no table of Ghidra's or radare2's tools (T-418).** The leftover table of their kinds, report sections, answer rows and aggregates (`core.builtin_reverser_kinds`) is gone. Any tool a decompiler or disassembler lists and does not declare is read by its verb and its object, in the words the platform's own consumers read: `list_imports` is `import_listing`, `list_exports` `export_listing`, `list_functions` `function_list`, `list_methods` `method_list`, `list_segments`/`list_sections` `segments`, `list_strings` `listing_strings` and `search_strings` `string_search`, `get_current_program_info` `program_info`, the callers and callees of a function `callers` and `callees`, `analyze_api_call_chains` `call_chains`, `detect_crypto_constants` `crypto_constants`, `analyze_dataflow` `dataflow`, `extract_iocs_with_context` `iocs_with_context`, `detect_malware_behaviors` `behaviour_scan`, `find_anti_analysis_techniques` `anti_analysis_scan`, a completeness check `documentation_completeness`, an analysis of a function `function_analysis`, a forced decompilation `decompile_refresh`, a load from the project `project_load` and an open of a project alone `project_navigation`; camelCase is read as words, and another verb of the same category reads the same. A batch tool's aggregates are read from its verb, object and arguments (`batch_decompile` over `functions` of `decompile_function`, so a held function still answers a later single read; `get_full_call_graph` of `get_function_call_graph`; `batch_set_comments` of the three comment tools). Every Ghidra and radare2 tool reaches the same consumers, report sections, evidence roots, function lists and image range as before; radare2's `list_all_strings` is read as holding strings rather than by a strings kind, which every strings reader reads alike; `bulk_fuzzy_match` no longer says it aggregates `find_similar_functions_fuzzy` (its verb is no other tool's), which only drops that line from its description. Under a block's `default_effects`, the reading that a tool sends the file it opens is dropped only for a tool read as opening or reading the file where it runs: a tool read as sending its bytes, a `utility` or `run` tool and one that runs what it is given keep the reading. A tool with an argument whose name holds a word for code, a script or a command (`code`, `script`, `command`, `python` …) whatever else it holds, unless its other words only name a property of it (`code_style`, `script_type`, `command_count`), or an expression evaluated as a condition or a filter, or, for a verb that runs or evaluates, a source, a query or an expression, runs whatever it is given, the block's own analysis step included, and a `run`/`exec`/`eval` verb with no such argument other than that step runs what its definition does not say. Whether an argument takes the file's content is one rule for every reading: its schema's format or contentEncoding, or a name for content (or data or a body beside a file's word) unless the schema types it a number or a flag (`max_scan_bytes: integer` no longer reads as content); a reverser tool that takes content is read as sending its bytes and is never lifted. A tool that says it submits, uploads or sends discloses unless it is marked read-only, and whatever its hints say when it takes a path, content, an id or a hash. A stored removal of a tool the block does not ship (`<tool>: null`) stays a removal, through a dump and its validation, but never of the reading that the tool sends the sample, and a stored change of a field read through a kind (`places`) is laid over the derived kind inside its reader's rows, as before.
