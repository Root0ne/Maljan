### Security

- **A job's staging on a reading server of its own is removed when the job ends (T-325).** The analysis and network servers, in containers of their own, offer `release_job`, a delivery primitive no model is shown: at the job's teardown the worker sends it, with the job's id, to each server a reading of that job ran on, while its session is still attached, and the server removes that job's staging directory (capa's and FLOSS's scratch, the unpacker's carves, a capture handed over) and nothing else. The id is turned into the one directory name the staging layout composes, a single path segment whatever it holds, so a `..`, a separator or an absolute path names nothing outside the staging base and no other job's directory; a link standing there is unlinked and never followed, and a server started for one job releases only that one. Every server is asked at once, each call capped at five seconds and the whole release at six, ahead of the servers' close inside the worker's 60-second teardown; a cancelled job releases too. A server that lacks the call, cannot be attached, refuses or does not answer is logged, its staging left to the 24-hour sweep, and the job is never held or failed by it. The call is declared under a kind of its own (`staging_release`), so a server that declares only it is never chosen to run readings.
- **A reading server refuses a data directory or a file argument that is not a string, and an empty rule directory (T-326).** `run_reader` checked a data directory only when it was a non-empty string: an empty `rules_dir` resolved to the project root, outside `/app/data`, and any other value reached the reading unchecked, as did a file argument that was not a string (a number would have named an open file descriptor). Such a value now raises `TypeError`, and an empty data directory is refused unless the reading declares it optional (capa's `signatures_dir`, where empty runs without library identification); an empty file argument is held to the server's confinement like any other path.

### Fixed

- **The isolation report places a pack reading where it ran (T-324).** A triage pack reading that ran on a server of its own was counted under the pack's own source and reported as read in the worker process. Each pack entry now records where its readings ran (`ran_on`: `mcp:<server key>` for such a server, `pack` for the worker beside one), kept on the evidence row (migration `20261031000000`, sealed in the ledger chain only when set) and served with it; the isolation part counts the entry under those servers, and the effects part places the emulator by them, so only a reading the worker ran is reported in process. An entry whose readings all ran in the worker, and every stored run, carries no such field and reads exactly as before.
