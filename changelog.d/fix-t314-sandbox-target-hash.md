### Security

- **A detonating sandbox whose report names another target than the sample is recorded, not failed (T-314).** Only an attached report's claimed hash was compared with the sample, once, at its upload; a sandbox that ran the sample during the job named its target in its own report and nothing read it. The app now keeps the target SHA-256 the provider's reader put in the neutral report for a detonation during the run that ended with a report (`container.sandbox_target_claim`, any sandbox provider alike), and the worker compares it with the hash the job ran the sample under on the completed, stopped and kept-after-failure paths. A different hash is logged, kept on the run summary as `sandbox_target` (`expected_sha256`, `sandbox_sha256`, `provider`, `task_id`; a value that is not a 64-character hex SHA-256 is kept on one line without control characters, cut to the sandbox-failure bound, with `sandbox_sha256_valid: false`, and said as such) and, where the disclosure record has an isolation part with rows, under `disclosure.isolation`, whose part in the report then gains one line naming the sandbox, its task and both hashes. The run is neither failed nor degraded for it. A report naming the sample's hash in any case or none, a task that ended without a report, a stand-in report, a mock sandbox's recorded fixture and an attached report add nothing; stored runs replay byte-identical.
