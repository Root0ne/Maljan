### Fixed

- **The console's server editor shows a block's trust in its server's own declaration as it is in force, and an operator's tick holds for the server it was given for (T-421).** A built-in block pointed at another server showed the trust it ships with while it was off, and a tick on it was the shipped value posted back, dropped on save, so the trust could not be given from the console at all; a saved built-in at its shipped server showed it off while it was on. The settings answer now serves each block's trust in force with the launch it holds for, a tick is recorded with the launch it was given for (`trust_granted_for`: a digest of the transport, command, arguments, working directory and address as written, so it reads alike on every host and after a release), and a save that points a trusted block at another server withdraws the trust (a built-in's falls back to what it ships, which holds only at its shipped server; any other block's is turned off). The editor shows the box off, and says why, as soon as the block is pointed elsewhere, until the operator ticks it again; the connection test reads the trust as the save would. A shipped value sent back is never read as a grant, a block that sends no grant (an older client, a script, a configuration file) is read as before, and a trust set in the block itself still holds. A provider block's settings gain the leaf, shown nowhere it can be typed.
- **A stored tool-declaration change naming no kind of its own no longer locks the console's tool declarations box (T-428).** A change such as `{reputation: {rank: 30}}` on a lookup whose kind comes from its server's listing showed in the box, and the box's strict reader refused every edit of the box until the entry was removed. A tool typed exactly as the box held it is now kept as it is and named below the box as kept as stored, as the API keeps a stored change sent back unchanged; every tool an edit adds or changes is still checked in full.
