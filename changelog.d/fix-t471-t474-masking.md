### Security

- **A path earlier in the same word no longer shields a password after it (T-471).** Where no backslash stood before the password, a Windows path at the start of the word or of a value refused the whole word, so `'C:\x','u:pss@h:8080'` and `f(C:\x,u:pss@h:8080)` kept `pss`. A path now ends at a `,` or `;`: where the word is refused as a path, the address is read from the last such separator before the first colon that is no drive's (`C:\`; `C:/` only at the start), or, for a token alone, from the last separator before the `@` where a quote or bracket follows it, escaped or not. The colons are read from the value the path stands in, so a JSON member's key names no user. `'C:\x','***@h:8080'`, `f(C:\x,***@h:8080)`, `('C:\x','***@h:8080')`, `{"a":"C:\\x,***@h:8080"}` and `{"a":"\\\\srv\\share,***@h/v1"}` keep the path and lose the credential. What follows the separator goes even where it could be a later name of the path (`C:\a,b:c@h:8080` keeps only `C:\a,`): no Windows name holds a colon. The known residual, a one-letter user name whose password begins with `/` and holds a backslash (`u:/p\x@h`), reads as a drive written with a slash and stays kept; `bare_userinfo` names it.
- **A WebDAV or hidden UNC share is kept again (T-474).** Since T-423 a UNC server name held only letters, digits, `_`, `.` and `-`, so `\\srv@SSL\DavWWWRoot\x@h/y` and `\\srv$\x@h/y` were masked though they hold no credential. The server's name may now end in `@SSL`, a port or both (`\\srv@SSL@443\`), or in a hidden name's `$`; no other `@` or `$` stands in it, and a backslash must follow, so `\\pw@h:8080`, `\\pw@SSL@h:8080`, `\\pw$@h:8080` and `\\u@pw@h:8080` are still masked. The accepted residual: a password written as such a share is (`\\pw@SSL\x@h:8080`, `\\pw@1234\x@h`, `\\pw$\x@h/y`) is kept, as `\\pw\x@h:8080` already was.
