### Security

- **A host with an underscore label, or one the run recorded, no longer prints live in a finding message, a tool's cell or a decompiled listing (T-357).** A finding message was defanged only by the reader of every host, which read no label holding an underscore, so a recorded service record such as `_ldap._tcp.dc._msdcs.example.com`, or a subdomain such as `cdn_.example.net`, printed as a link beside the title, §1, §4, the validation list and the export decisions. A finding message is now read with the run's own recorded values first, as a tool's text is, and so is every escaped cell a section writes (a sandbox request's method, status and user agent, carve notes, obfuscation indicators, the IOC table's where and notes, coverage lines). The reader of every host reads a name with underscore labels, after a space, a path's slash or a run of dots and in any case, where the labels after the last underscore are a host it reads alone, so an unrecorded service record is defanged too, while an identifier such as `FUN_00401310`, `__init__.py` or `self._data.items` prints as written. The closing pass over every section reads the run's own values as written and as an escaped cell writes them (`cdn\_.example.zip`), so a recorded host the reader of every host leaves as written is defanged wherever a section printed it. A decompiled listing's caption and code are defanged the same way when it is drawn, and the HTML and PDF read a stored report's figures again (each caption and legend, a listing's code, every drawing's labels such as a process name or a section name, which are also defanged when drawn), so a PDF viewer links nothing in a figure drawn before this change. §10.2 now says that each draft rule's body is printed as written, its network values not defanged, so it compiles as deployed. Stored runs re-render unchanged apart from that one line.
