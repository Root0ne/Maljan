### Changed

- **The product is Malspark everywhere (T-576).** The Python package and distribution are `malspark` (`import malspark`, the `malspark` command), environment variables start with `MALSPARK_`, the containers, images, networks and the compose project (`name: malspark`, so volumes are `malspark_<volume>`) use the new name, and so do the Postgres database and user defaults, the Qdrant collection defaults, the MinIO bucket default, the entry-point groups plugins register under, logger names, the WebSocket subprotocol, the refresh cookie, the token issuer and audience, the console's browser storage keys and page titles, generated rule names, download file names, STIX custom properties (`x_malspark_*`), the settings export format (`malspark-settings/3`) and the job package format (`malspark-job-package/2`). The repository is https://github.com/Root0ne/Malspark and its GitHub Pages path is `/Malspark`. New job packages are signed under the key label `malspark-job-package-v1`. What stays as it was: every reader takes a format or schema label written under the previous name as the same version, so a settings export, a job package, an evidence bundle and the frozen tool-facts snapshot written before still import, verify and read; a package signed under the previous key label still verifies; a STIX bundle stored before is served under the new property names; and the domain tags of the evidence ledger, the audit chain, the stored-report seal and package signatures, and the ledger chain's key label, are unchanged, so every stored chain and seal still verifies (`malspark.core.previous_name`). MISP attribute uuids, the STIX producer identity and the settings repair markers keep their values; a tool server's previous `_meta` key, a plugin in a previous entry-point group and a stored server map's previous environment names are still read (a migration renames the clear map); an environment variable still set under the previous prefix is named at start; the previous default staging base is still swept.

### Upgrading

- **Carry a deployment across before starting the renamed stack (T-576).** Stop the old stack without removing its volumes and run `scripts/upgrade/rename-volumes-and-env.sh`: it prints the plan, and with `--apply` copies the old volumes into the new names and renames every key in `docker/.env` that has the old prefix to `MALSPARK_`, printing key names only; where the copied MinIO data holds the old bucket it sets `MINIO_BUCKET` to it, which compose now passes to the API and workers, so samples, spilled parts and anchored audit heads stay under their object lock; with `--qdrant-url` it aliases the new memory collection names to the old collections. It also prints how to rename the Postgres database and role or keep them, how to point memory at the existing Qdrant collections, and how to copy the stored samples into the new bucket. Signed-in sessions end once. `docs/upgrade-from-previous-name.md` walks through every step.
