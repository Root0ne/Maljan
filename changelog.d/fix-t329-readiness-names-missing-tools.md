### Fixed

- **A tool whose library or executable is missing is named before the job starts, not after the run (T-329).** A run whose host had lost the `capa` extra passed `POST /jobs` and only said DEGRADED RUN after it had been paid for. The in-repo stdio servers' declared needs now live in `maljan.tools.sidecar_needs`, which each server still builds its capability manifest from, and `POST /jobs` checks them, without starting anything, for every server the job can call that is switched on and launched on this interpreter, and for every triage pack reading the worker runs itself (any whose declaring server is not both switched on and reached at an address, whatever that server's block says): a module is looked up on the import path and an executable where the server would look for it. Nothing runs on a sample. The job is still accepted (there is no setting that refuses on an unavailable tool, and none is added); its answer carries `unavailable_tools`, each with the server, the tool, the server's own reason, the remedy, what it still answers and the words the run's degraded block would use. `GET /system/status` carries the same list for the default team to signed-in callers, and the dashboard shows it. capa and YARA now name their own extra in the remedy (`uv sync --extra capa`, `uv sync --extra yara`) instead of the `tools` extra. A server whose block sets `PYTHONPATH` has its modules left unchecked. A server reached at an address, or on another interpreter, is still described by its own manifest at attach and by the connection test. `scripts/rehearsal/run.py` now fails a run that carries any degradation reason, printing each one, unless the reason is allowed by name with `--allow-degradation` (the words before its parenthesis, e.g. `server.analysis.capa_unavailable`). A fault scenario declares the reasons it causes on purpose (`SCENARIO_DEGRADATIONS` in `scripts/rehearsal/roles.py`: `cut_at_cap`'s unwritten sections, `deadline_hit`'s job-timeout note), and the gate allows exactly those for it; any other reason, and any reason on the normal scenario, still fails. Stored runs read as before.
