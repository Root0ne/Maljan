### Fixed

- **On Claude, a validation retry's first turn is cached once and read by the questions after it (T-393).** A validation retry is a tools-free conversation built from text: the evidence as its first user turn, the answer it fixes, the question. The drops question and the whole-answer question that follow it send that first turn again (the whole-answer question the retry's question too), yet every one of these requests was billed uncached: the request hook placed its breakpoints on the right turns but skipped a turn written as one string. The turn before a request's newest assistant turn is now sent as one text block holding the same text, carrying the breakpoint the policy already puts there, and keeps that shape on every later request of the model, marked or not; a turn a thinking block was written after as a string keeps its shape, so the local prefix check and the cache prefix bytes stay unchanged, and the binding digest reads a string and its one text block as the same turn, as the API does; any other turn, the newest included, is listed only where an earlier request of the model listed it. The model reads the same text. On haiku7's stored requests, put through the hook as it is now, the 31 retry, drops and whole-answer requests change shape and no other request changes; the 37 single-shot calls the run billed 3.77 USD come to 3.57 USD (drops question 0.48 → 0.28, whole answer 0.45 → 0.31, retry 1.54 → 1.69 for the cache write). The cited ledger entries these turns carry are kept whole: none of them is already in its request (none of the 357 thousand tokens of entries shown repeats text its request holds), and naming entries to stay under the 100,000-token price tier would hide them, so neither is done.
