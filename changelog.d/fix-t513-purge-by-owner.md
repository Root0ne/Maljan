### Added

- **An admin purges long-term memory by owner prefix (T-513).** Memory an isolated job files under an owner key of its own, below its account's (`memory_owner_for`: the account's key, `ISOLATED_JOB_SCOPE`, the job's id), is read by nothing again. The purge's path separator is read off `ISOLATED_JOB_SCOPE`, so the two cannot drift, and `isolated_jobs_prefix(<account>)` names every isolated job's memory of one account and never the account's own. `POST /system/ltm/purge-owners` (`{"owner_prefix": ..., "whole_account": ..., "dry_run": ...}`, a bearer-session admin only) removes every case and function hash filed under an owner at or below the prefix, from the in-memory store, from Qdrant and from the function-hash collection beside it, and answers the counts per kind; a dry run counts and removes nothing. The prefix is read a path segment at a time (`long_term_memory.owner_under`): `<uid>/job` names that path and everything below it, `<uid>/job/` only what is strictly below, and neither names the account's own key, `<uid>/jobs`, another account whose id begins with the same characters, or an unscoped entry; an account id sent in upper case is read as filed. A single segment, a whole account, is refused unless `whole_account: true` is sent. A prefix that names no owner path (empty, an empty segment, over 512 characters), an unknown field, a backend that cannot purge by owner and a purge that matches nothing are refused, so a mistyped prefix is said, never answered 0. A purge leaves an `ltm.purge` audit row with the prefix and each kind's count; one that fails part way leaves `outcome=failed` with the error class and what each kind had lost (`memory_repair.OwnerPurgeFailed` names the ids already deleted per collection). No schema change.
