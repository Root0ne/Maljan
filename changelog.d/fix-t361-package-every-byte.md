### Security

- **A job package reads `broken` for any change to its bytes (T-361).** One flipped byte could read `verified` (the gzip header's flags, time, compression and system bytes are covered by no CRC, and deflate is not canonical: a match in a run of zeros may point at any earlier zero, so the archive and its CRC stay the same), and run outside the test's key fixture the same flip read `seal_unverifiable`. The gzip header now carries the file's own digest in an extra field: the SHA-256 of every byte after the header and, for a signed manifest, an HMAC-SHA256 of it under the package key (zeros when unsigned). `python -m scripts.package.verify` reads the file once, front to back, hashing every byte as the archive is read and then the rest to the end, so a flipped, cut or appended byte reads `broken` (naming the entry a check of the archive caught it in, or else the package) before the seal is looked at, and checks the HMAC once the signature is known, so a signed package re-encoded without the key reads `broken` too (`other_key` where that key is not held); an I/O error while reading reads `broken`; `seal_unverifiable` keeps its meaning of a key, seal or run file the package lacks. The verdict carries `file_digest` and its reason. New packages say `maljan-job-package/2`; a package built before (`maljan-job-package/1`, plain header) still verifies as it did and reads `file_digest: legacy`, compared byte for byte with what the builder wrote then (gzip header, every tar header and padding byte, end marker, record padding, CRC, length, nothing after), so only an equivalent deflate encoding of the same archive goes unseen. A current manifest under the old header, or an old one under the new, reads `broken`, and so does a signature file that is not byte for byte the record the builder writes (a changed `manifest_sha256`, algorithm or label, an added field or other spacing), in either format. The test flips every offset of a built package by one bit and by 0xFF.
