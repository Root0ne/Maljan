### Fixed

- **A whole-function read the ledger already holds is answered from its entry, not run again (T-367).** A call of a tool that declares it reads one whole function (`kind` `decompile` or `function_disassembly`) and changes nothing (`read_only`) is answered before the tool runs in two cases. The first is an earlier call written exactly the same, whose answer is a listing; a bare spelling of an address is never answered from a `0x` call. The second is an earlier call, on the same server, of a tool that declares itself this tool's aggregate (`aggregate_of`). That call must give its declared roles and exactly one other argument, a list of addresses. Its answer must be one JSON object whose keys are all addresses on that list, written `0x…` or bare with six hex digits or more, and one key must name this function. The single call must give a `0x` or bare address, the same declared roles (the same `program`, or none on both sides) and no argument nothing declares. An address given as a number, a key named twice, and any other argument the aggregate's call gives (an `image_base`) answer nothing. Everything is read off the declarations and the answer's shape, never a tool's name, and a tool that declares nothing keeps running. The held answer must be one the model read whole and the entry holds byte for byte. It answered and is settled, with nothing cut, shortened or marked partial, and it is a whole listing: not empty or prose, with braces balanced and closed on its last line, and a last line that ends in no ellipsis and says nothing of a cut, a time-out or a partial answer. Each job counts the calls on each server that may change state, as they start and as they end, for every agent of the job, delegates included; one on an unknown server or the team server counts for every server. A read that ran while the count moved is not held, and a held answer is not handed out once the count has moved since its read started. The model reads the held text exactly as the entry recorded it, stamped with that entry's id, with a sentence saying it came from an earlier call. The call is filed as a repeat of that entry and counted as an identical call that ran is counted, so the third ask is still refused and the loop's end comes at the same point. Where the conversation has no room for the text, the tool runs and its guardrail decides. The stored loops were replayed through the recorder: haiku5 (`tests/fixtures/clearing/haiku5_tool_loops.json`) and the stored runs haiku2–5, run–run7, local3, local4, local6 and local8. In those loops 8 calls are answered from the ledger: 5 batch members (run3 3, run4 2) and 3 identical reads (haiku4 2, local4 1). In each case the answer is byte-identical to the held entry's text and to what the tool answered when it ran. haiku5's eight batch-member reads still run: five pass a `timeout` that nothing declares, and three give a `program` that only one side named.
