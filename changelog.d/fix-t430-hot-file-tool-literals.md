### Fixed

- **No server's or tool's name sets a call budget, marks a server as shipped, or reads a function's auto-name (T-430).** A tool server whose block declares no `call_timeout_seconds` (every built-in) got, per call, the longer of `core.static.capa.timeout_seconds` and `core.static.yara.timeout_seconds`: two blocks named for one provider's tools set every other server's budget. That budget is now a setting of its own, `core.mcp.breaker.default_call_timeout_seconds` (default 300, the floor as it shipped), read alike for every such server whatever it or its tools are called; a renamed copy of a server gets the same budget and the same long-running tools as the original. The drafted YARA rule's check against its sample, which also read `core.static.yara.timeout_seconds`, has its own budget, `core.reporting.detection_rule_check_seconds` (default 60). Revision `20261102000000` writes a deployment's stored floor into the new budget, so no server's budget changes, and moves a stored YARA timeout to the check budget as it is; it is reversible. An export is now written as `maljan-settings/3`; `/2` and `/1` are still imported. An older export's YARA timeout becomes the check budget, and where a `/2` or `/1` document carries either static timeout and no call budget, the call budget is given the floor it carried (`legacy_tool_tables.former_call_floor`, the rule the revision restates, held to it by a test); a `/3` document's static timeouts are their own. A store row the revision has not moved yet is read as the key that now holds it where no settings model reads the old key itself (the YARA timeout); `static.r2.mirror_dir` and the flat `memory.qdrant_*` keys stay with their own models, which refuse what they cannot read, as before. Known limit: running the revision again after a downgrade reads a check budget set in between into the call floor, as the YARA timeout it was moved back as. A server is shipped by a mark its seed carries (`MCPServerConfig.shipped`), set on the deployment's seed and on a stored block re-seeded under it and never read from what is stored or posted, instead of a table of five keys: the stage switch `builtin_tools: false`, the judge's asks, the stdio launch environment, the order servers are attached in, the server map's save and probe, and the keys the console is served all read the mark. The container sidecars the deployment seeds (`die`, `ilspy`, `goresym`, `yarax`, `oletools`, `webcrack`, `unblob`, `jadx`), which the table had missed, now carry it too: a stage that withholds the built-in tools withholds them, the console offers no Remove for them (a removed one came back on the next load), they no longer count as a server of the operator's own in the generic static guide, and they are still attached as before. Attach order reads a second seed mark (`MCPServerConfig.attaches_as_builtin`): a seed that ships switched on, or that leaves its binding to the definitions (VirusTotal), attaches with the built-ins, and one that ships off and bound to roles of its own (the sidecars) runs only once an operator switches it on and attaches after the definition's own servers, as an operator's server does. Every tool name stays exactly as before: a referenced server keeps the bare name of a tool it shares with such a sidecar (every server's `capabilities`), and VirusTotal bound to a role keeps its names over an operator's server. A probe of a shipped server starts it with its seed's marks, as a run does. The validation's unused pattern of the shipped auto-name prefixes is gone; every check reads the declared prefixes (`generic_function_name`). Stored runs replay the same.
