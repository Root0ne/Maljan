### Changed

- **A provider tool reference can name its provider, so one agent holds several static providers (T-505).** `ToolRef(kind="provider")` takes an optional `provider` id: unnamed, it is the definition's own static provider exactly as before; named (`{"kind": "provider", "provider": "<id>"}`), it is that provider's tools, so a `generic` or `lead` definition can hold the tools of two or more providers at once. Each provider is opened for the agent under the job (ledger, output limit, context budget), pinned to its own mirror of the sample, mirrored for by the worker, checked by the job-start readiness check (a provider named on a reference counts as given by name) and closed with the job, as a definition's own provider is. A later provider's tool whose name an earlier one already holds is offered as `<provider>__<tool>`, its declared name kept, the rule tool servers already follow; the prompt carries each provider's own text, read against that provider's tools, and one sentence about the tools naming every provider. A team that forces a static provider of its own forces it on every reference, so the `measurement` baseline stays tool-free. An unknown provider id on a reference is refused at the reference, by the settings model and by the settings API. The console's agent editor offers one row per static provider beside "its static provider's tools". A reference that names no provider is stored, dumped and resolved exactly as before, so stored settings, agent definitions, prompts and stored runs of existing configurations are unchanged.
