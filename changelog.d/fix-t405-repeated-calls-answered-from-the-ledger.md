### Fixed

- **An identical call of the job is answered from the job's earlier entry, across agents and rounds (T-405).** haiku7 asked VirusTotal for the same two domain reports eight times (four agents, two domains) and for the same file report four times, and no entry was answered from the ledger. A call is now answered from the entry that holds its answer when it is the same tool on the same server with the same arguments in the same job, and the tool's own MCP server marks it both read-only and idempotent (`readOnlyHint` and `idempotentHint`). The hints are taken as the server's own statement that a call changes nothing and has no further effect when repeated. They are not taken to mean the call answers the same: a settled-answer check guards against answers still pending. A read-only mark alone is not enough, and a tool its server says nothing of keeps running. A declaration may only veto, never grant. One that states the tool is not read-only keeps it running whatever its hints say. So does one whose kind's answer moves by what it means, from one table of kinds: a status, an analysis status, a sandbox status, a submission or a submission's status. A declaration silent on both leaves the hints to decide. The answer is reused only within the job, never across jobs, and only when the earlier entry holds it whole: answered and settled, with nothing cut, shortened or marked partial. For another agent or round, an answer counts as settled only when no status or state at any depth of its structure is still waiting (`{"data": {"attributes": {"status": "queued"}}}`) and no reason, error or message stands anywhere in it; a lookup whose status is `found` counts as settled. A poll still waiting runs again. An agent's own loop, its revision rounds and its chunks keep reading the top level of an answer exactly as before. A failed entry is never reused, and a call whose earlier answer was cut runs again and returns what it asks for. A call on the same server that may change state, by any agent, makes the held answer stale. So does every attach of the server, whether a reconnect, a restart, a per-loop copy of its process, or a static provider's own server, counted under the server's name and where its tools are declared. A static provider's function-hash walk on its server counts too, as it starts and as it ends. An answer read through one handle of a server is served through another handle only when that server exposes no tool that may change it. A whole-function read is also answered from another agent's batch entry when both qualify and the batch tool's declaration names the read among the tools it aggregates (`aggregate_of`). The model reads the same text under the earlier entry's id, with a sentence saying that entry answered it. The call is filed with `repeated_of` set, and the loop's repeat guard counts it as an identical call that ran, so the loop still ends at the same point. Replayed offline through the recorder, haiku7 has 8 calls answered from the ledger: 6 `get_domain_report` and 2 `get_file_report`. That saves 8 VirusTotal lookups and 8.2 s of tool time. Each answer differs from what the tool answered when it ran only in VirusTotal's `retrieved_at` query time. Its Ghidra, radare2 and analysis-server calls still run, because those tools carry no server hints.
