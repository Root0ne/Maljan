### Changed

- **The report draws a rule tool's answer by what it is, never by which tool gave it (T-418).** The evidence sections of the three rule kinds were drawn by three readers named after the tools that first filled them, each reading that tool's own fields, and the renderer, the run comparison and the narrative's rule pointer found the tables by keys spelled with those tools' names. One reader now draws every `signature_rules`, `event_rules` and `capability_rules` answer, from a table per kind (`ledger_report.RULE_TABLES`): the kind's columns, each read at the value the tool declares under the column's name, else at the field the kind's answers share (a rule-match list's rule, tags, level and matched fields; a capability list's namespace, rule, ATT&CK ids and MBC), and the technique column at the declared techniques or the row's ATT&CK tags. The table's key is its kind's (`section_key_of_kind`), kept as the key stored reports, the replay and the console already read (`yara_matches`, `sigma_matches`, `capa_capabilities`, now aliases held with the other stored names), and the Markdown renderer's capability table, the run comparison's detection rows and the narrative's rule pointer read the tables through it. A table that holds the rows of more than one tool of its kind now says which tool each row came from (a `Tool` column, added only then, so a table one tool filled is drawn as before), its title names every tool, and the run comparison labels each row by its own tool, the narrative's rule pointer names every tool and the capability note names every tool whose rules fired; before, every row stood under the first tool's name. A stored report with no recovery record finds an emulator's string table by the kind its entry declares and the fields that declaration reads the scheme and the text under, not by one tool's section key. A tool on a server never seen before that declares one of these kinds and answers in the built-in's shape gets the built-in's table, rows and comparison rows unchanged; a tool its server declares nothing for keeps its whole answer in a generic block of its own, as before. The generic block stays one per tool, since each holds an answer in its tool's own shape. Stored reports re-render byte for byte, the sections rebuilt from their ledgers are unchanged, and every stored run replays as on origin/dev.
