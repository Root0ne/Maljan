### Changed

- **A stored run reads its tools from a frozen snapshot, never from the declarations a release ships (T-418).** A ledger entry written before entries recorded their source and facts (16 of the 19 stored benchmark runs hold such entries) was read by its bare tool name through the built-in tool declarations and the consumers' legacy name lists as they stand in the running release, so any change to a shipped declaration changed how every stored run read. What those tables gave is now frozen in one versioned, digest-pinned data file (`data/legacy_tool_facts_v1.json`: 288 tools with every field their declaration set, and each consumer's legacy names), and the legacy reading reads that file alone, as do the readers that held such an entry against the shipped tools (whether an answer is shaped as the built-in of its kind, the rule matchers a statement may name, the argument names a produced layer is read under). The check whether an answer is shaped as the built-in of its kind holds every entry, live or stored, to the shape that kind's reader code was written for, which is the frozen one, until the kind-keyed builders read declared values; a file whose digest is not the pinned one is refused rather than read. The snapshot is never regenerated. A test holds it equal to today's tables tool by tool and field by field, and others show that emptying the shipped tables, giving their tools other kinds, or reshaping them with each kind kept (rows, places, display names, sources, arguments) no longer changes how a source-less entry reads. Entries that stored their facts read as before, the shipped declarations themselves are unchanged, and every stored run replays byte for byte as it did.
