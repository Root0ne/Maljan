### Fixed

- **A sandbox packet capture that fails to fetch is no longer lost silently (T-336).** The Triage provider returned nothing, with no log line, when the capture download answered an HTTP error, raised, or wrote an empty file, so a run lost every capture-derived indicator and neither the run summary nor the report said so. Every sandbox provider that fetches the capture (Triage, CAPEv2 and the described REST sandbox) now goes through one fetch: a 5xx other than 501/505, a 429 or a dropped transport is tried again, up to three attempts in all, waiting the status poll's own interval backed off 1.5x to 60 s, or a `Retry-After` the sandbox sent. The fetch now runs off the event loop like every other sandbox call, so the worker's heartbeat, cancel poller and job clock keep running while it waits; its waits are clamped to the job's sandbox deadline, a retry past it stops with the cause `deadline`, and a cancelled job neither waits nor tries again (`cancelled`). A truncated Triage overview is asked for again. A capture fetched but then not attached is removed and said as `attach <Type>`. Each failure is logged with its HTTP status or exception type, never a URL or the exception's text. A capture that still cannot be fetched becomes a degradation reason that names it and why, such as `packet capture not fetched (HTTP 502)`, and an empty file has its own, `packet capture fetched empty (4 bytes)`; the reason reaches the run summary, the report and the UI banner with the other reasons. The coverage record's "could not establish" block now says "the packet capture could not be fetched (HTTP 502)" in place of "the sandbox report names no packet capture", which stays the words for a sandbox that offered none (a 404, no behavioural task, or CAPE's refusal envelope). Stored runs re-render unchanged.
