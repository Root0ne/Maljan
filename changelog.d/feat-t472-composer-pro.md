### Added

- **The composer writes the analyst report's own prose (T-472).** Four sections beside the technical spine, each a call of its own in the same round: the executive summary's capability bullets (at most eight, subject first, most actionable first, followed by the platform's verdict, family and severity line in words), a conclusion of two or three short paragraphs under the platform's verdict sentence, one scoped limitations paragraph, and one sentence of procedure per published ATT&CK technique. The analyst report prints each where the composer wrote it and what it printed before where it did not. Where a composed section replaces the platform's text (the key findings and the summary paragraph, the judge's words in the conclusion, a technique's first claim sentence), the replaced finding or sentence stays when a check marked it or when it names a value (a host, an address, a path, a code span, a quoted string, an ordinal call such as `x.dll,#1`, an identifier with a digit or an underscore) printed nowhere else in the report. The likely targets and the sophistication line stay after the conclusion; every platform sentence of the limitations stays after the composed paragraph. The summary and the conclusion are written from the summary paragraph, the key findings and the capability overview, not from every claim in force, so each call stays small.
- **The execution flow is drawn, and a recorded message is laid out field by field (T-472).** From two steps up, the analyst report's Markdown carries the flow as a Mermaid diagram and its HTML and PDF draw it as an inline figure, each box the step's first sentence and its observed or assessed mark. A channel whose recorded message format is `name=value` fields gets each field on its own line with what its conversion holds (`%d` a decimal number, `%s` a text) and the value of a configuration item of the same name. With no such record there is no example.

### Changed

- **Every composer section is held to the analyst report's style (T-472).** The system text tells each section to anchor each statement on its concrete value, to say confidence in words, to use no words about how the report was produced (its ledger, the judge's rulings, tool calls, claim numbers, the analysts' names), to scope its negatives, and which section owns which fact, in the report's order. A check of every answer finds a confidence number attached to the word (`confidence 0.85`, `0.35 confidence`, `85% confidence`) and those phrasings, an agent's identifier name among them; a phrasing the section's own prompt shows is the evidence's term and is not asked about. The section is asked once, a parsed structured answer included, and a sentence that stays is marked where it stands (`report.numeric_confidence`, `report.process_words`), never rewritten. The four new sections' shapes are asked about the same way (`report.prose_shape`), and so are a key-finding value no bullet carries and the report states nowhere else, and a value a procedure dropped from its technique's first claim (`report.value_not_carried`).
- **The analyst statements only the ATT&CK section held are given to the sections that own their facts (T-472).** The statements of a technique a rule matched only on names resolved at run time are shown, as claims, to the functionality or command-and-control subsection of the technique's tactic, so their values are written where they belong; the appendix that prints a statement naming a value printed nowhere else stays, and empties as the sections take them in.

### Fixed

- **A channel row is bound to the code that holds its values (T-407).** The C2 section is told that each channel is one piece of code's traffic and gets only the endpoints, verbs and strings an entry shows that code using, and is shown the functions the recovering tools name around each network value. A check reads, in the run's entries, the code addresses of each record holding a value a row gives: a value held beside another row's code and none of its own (a verb a different routine references), or an endpoint two rows naming different code both give while the records hold neither's code, is asked once (`report.channel_binding`). The haiku7 table that gave the payload fetch at 0x8d90 the check-in's `/live/` URLs and the `GET` string 0x5030 references is now asked about on that row.
- **The encryption table is asked for by its fields (T-408).** The section's instruction describes every field (an extension is the one appended to each file the sample encrypts) and says to fill a field only from an entry that shows its value for this sample, with an example answer whose unsupported fields, the extension among them, are null; a field left null prints no row.
