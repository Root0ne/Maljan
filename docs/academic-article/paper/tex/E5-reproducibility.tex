\section{Reproducibility}
\label{app:repro}

\subsection{How the numbers in this paper get onto the page}\label{numeral-policy}

Every number this paper states about its own results is generated from the
committed per-sample records into a macro and referenced, never typed. A key the
document asks for and the derivation cannot produce stops the build rather than
leaving a hole in the page. The reason is drift and not tidiness: over this
project's history the same measurement was typed into five places and went stale
in all of them, a superseded interval survived a correction because it had been
typed rather than referenced, and a figure caption disagreed with the paragraph
beside it for a month.

The rule is scoped to its reason, and the scope is stated here rather than left
implicit, so that a reader can tell a deliberate exemption from an oversight.
Three kinds of number are deliberately literal.

The first kind is settings. A port, a thread count, a context length, a step budget, a GPU model.
No analysis produces them and they cannot go stale, so they are marked
\texttt{\textbackslash setting\{\}} in the source at the point of use, because the distinction is
not visible in the digits; \setting{31}\,GiB of host memory is a setting and
\fact{paged-out-working-set} paged out is a measurement, and both are a number and a unit. The
second kind is values quoted from cited work, since no derivation of ours produces someone else's
result. These are registered with the citation each belongs to and are permitted only on a line that
carries that citation, so a quoted figure cannot drift away from its source and become
indistinguishable from one of ours. The third kind is observations whose raw output was not
retained. A handful of the incidents in Section~\ref{sec:failures} were seen in diagnostic sessions
against live containers rather than in a study, and those sessions were never in scope for the
retention rule, which is Section~\ref{sec:threats}'s point arriving one more time. Each is
registered with the dated record that carries it and is presented as an observation rather than a
measurement from the archive.

A check enforces all of this, and refuses the third and second categories
without their record or their citation. It also refuses a
\texttt{\textbackslash setting\{\}} whose value is one the analysis already
derives, because that would be a way of laundering a measurement into a
constant.

\subsection{Hardware, and the ceiling it imposes}\label{hardware-and-the-ceiling-it-imposes}

Single host: RTX \fact{host-gpu}, \setting{31} GiB RAM, \setting{16} threads. Three measured properties that shape what can be
reproduced here:

\texttt{llama-server} grows with cumulative requests and does not plateau, at
\fact{llama-rss-fresh-gb} GB fresh, \fact{llama-rss-growth-gb} GB after a single full analyst pass,
and \fact{llama-rss-sustained-gb} GB after \fact{llama-rss-sustained-minutes} minutes of multi-arm
load. The growth is anonymous and unreclaimable, so it can go to swap and nowhere else, which on
this host is the ceiling on how long any run can be. A long paired run must therefore restart the
server between arms; the restart changes no decoding parameter, so it is measurement-neutral.
\texttt{scripts/run\_with\_restarts.sh} does this from the checkpoint, and is released with the
rest. An evaluation that outlasts its own instrument needs the cycling to be part of the method
rather than something the operator remembers.

Serving at \setting{64}k instead of \setting{131}k does not lower the peak, at
\fact{llama-rss-64k-gb} against \fact{llama-rss-growth-gb} GB. The baseline is CPU-resident expert
weights, and the growth follows the context a pass actually consumes. Generation rate also varies
from \fact{generation-rate-high} to \fact{generation-rate-low} tokens/s across requests. On this
hybrid recurrent architecture, llama.cpp writes and erases a \fact{recurrent-checkpoint-mib} MiB
recurrent-state checkpoint every few hundred tokens at \textasciitilde39k tokens of context, so
long-context calls are not slow in proportion; they fall off a cliff.

The Ghidra container is capped at \fact{ghidra-mem-limit-gb} GB (\texttt{mem\_limit}). Its JVM \texttt{-Xmx4g} bounds the heap only;
the database is memory-mapped and measured RSS reached \fact{ghidra-rss-gb} GB against that nominal \fact{ghidra-jvm-heap-gb} GB cap. Two
host lock-ups preceded this limit being added.

\textbf{The working set does not fit alongside an interactive session, and that is a reproducibility fact
rather than an operational one.} Model server \textasciitilde16 GB, analysis worker \textasciitilde8 GB, disassembly container
up to \fact{ghidra-mem-limit-gb} GB: on a \setting{31} GiB host this leaves nothing for a desktop. When we ran a paired study without
that headroom, the swap file was exhausted, the model server had \fact{llama-paged-out-gb} GB of its own address space
paged out, and one arm then exceeded a \fact{salvage-budget-seconds}-second budget on a \fact{static-max-chars}-character prompt. A model
generating from disk-backed pages is a different instrument from one generating from RAM, and the
timings it produces are not comparable to the rest of the table.

Two consequences for anyone reproducing this work;

\textbf{Give the run the machine.} Long paired studies here are run against an otherwise-idle host.
This is not a performance recommendation; arms measured under memory pressure are not commensurable
with arms that were not.

\textbf{Record the host state per arm, not per study.} Our harnesses capture \texttt{MemAvailable},
\texttt{SwapFree} and the model server's resident-versus-swapped split at both ends of every arm,
and the scoring script excludes arms whose host was degraded. This screen can only be applied
forward, because for arms already collected without it the state is gone and the honest label is
\texttt{unattributable}. That is the label our own halted ablation carries.

\textbf{Start the model server in its own cgroup, not the harness's.} This one cost us three
interrupted runs before we read the kernel log carefully enough.

\begin{verbatim}
task_memcg=/user.slice/.../snap.code.code-*.scope, task=llama-server
Out of memory: Killed process (llama-server) oom_score_adj:\fact{oom-score-adj}
snap.code.code-*.scope: Failed with result 'oom-kill'
\end{verbatim}

The harness had launched the server as a child process, so it inherited the cgroup of whatever
started the harness, an editor's integrated terminal, and its \textasciitilde16 GB was accounted to
the editor's scope. We had already made the server the kernel's preferred victim, and that was the
wrong level, because choosing \emph{which process} dies cannot change \emph{whose accounting it dies
inside}. Launching it as a transient unit with an explicit \texttt{MemoryMax} puts the measurement's
memory where it belongs and lets the server hit a limit of its own before the host has to
arbitrate.

\subsection{The sandbox, and three things that will block a reader}\label{the-sandbox-and-three-things-that-will-block-a-reader}

CAPE 2.5 at a private address, reachable only from one network.

It has one analysis machine (\texttt{win10}, x64) and no Linux VM, so only Windows PE can be
analysed dynamically whatever the code's stated scope, which is why the cohort is Windows-only. An
ELF submitted there joins the \fact{cape-backlog} tasks that are never scheduled. Reports are
retained for days rather than indefinitely; sampled across the full task-id range,
\fact{cape-report-retention-sampled} of \fact{cape-report-retention-sampled} older tasks return
\texttt{"Reports\ directory\ does\ not\ exist"}, while a report from four days earlier survived. The
local archive of fetched reports is therefore the only copy, and ``submit the same samples'' is not
a reproduction recipe on its own. The instance also rate-limits, and its throttle response is
byte-identical to its auth refusal, \texttt{\{"error":\ true,\ "message":\ ""\}} in both cases. A
harness that reads that string as a capability verdict will mis-classify a throttle as a missing
permission, as we did, briefly. Re-call a tool that worked minutes earlier to tell them apart.

Timing, for planning. A new Windows submission is scheduled in \textasciitilde1 second and completes in
\textasciitilde5.5 minutes; the \fact{cape-backlog}-task backlog is never scheduled and does not queue ahead of new work.
An n=\fact{cohort-n} cohort is roughly \fact{cohort-sandbox-hours} hours of sandbox time.

\texttt{max\_completion\_tokens}, which \texttt{ik\_llama.cpp} does not read; the cap must also travel in

campaign.

never \texttt{"length"}, and carries no \texttt{stopped\_limit} field. Telemetry that detects truncation by finish
reason will report zero however often the cap binds; compare the generated-token count against the
cap that was requested instead.

\subsubsection{The original frontier arm}\label{the-original-frontier-arm}

OpenRouter, \texttt{nvidia/nemotron-3-super-120b-a12b:free}, temperature \setting{0}, \fact{consensus-budget}-token output cap.

The free tier allows \fact{openrouter-daily-limit} requests per day (\texttt{X-RateLimit-Limit:\ 50},
\texttt{limit\_source:\ openrouter\_free\_tier\_daily}), resetting daily, with a \fact{openrouter-burst-limit}-requests-per-minute cap
that applies whether or not credit has been purchased. The first attempt at this arm exhausted
the daily quota mid-flight, \fact{quota-calls-landed} calls landing and \fact{quota-calls-refused} returning HTTP 429, and the n=\fact{superseded-frontier-n} estimate it
produced was not merely imprecise but pointed the wrong way (Section~2). The arm reported above is the
completed n=\fact{arm-default-n} run, taken from a fresh quota: \fact{arm-default-n} of \fact{arm-default-n} parsed, \setting{0} refusals, \$\setting{0} charged against
the \$\setting{25} ceiling.

The quota is stated here because it governs what a cohort-scale frontier arm costs in wall-clock
rather than in dollars: one call per sample over a \fact{baseline-n}-sample cohort is two days at \fact{openrouter-daily-limit} requests per
day, and a full-pipeline arm, roughly \fact{requests-per-analysis} model requests per analysis, is not reachable on the
free tier at all. The spend meter is enforced as a precondition on every call rather than reconciled
afterwards, and projections price output at the full cap because a degenerate decode produces
exactly that.

Two of these exist only because a result could not be believed, and both are worth running before
the studies they check rather than after. \texttt{verify\_b3\_mechanism.py} recomputes each ablation arm's
cascade set from its seeded fixture and compares it against what the arm recorded; it is what
established that a published finding of ours had measured the reconciliation step rather than a
model. \texttt{probe\_outbound\_parameters.py} asks whether the server acts on each parameter we send it,
by behaviour rather than by reading a response field, because a server that ignores a parameter
does not report having done so.

The judge-contribution study is run twice, in two conditions, and the pair is kept. Once with
the output cap not reaching the server and once with it binding. The comparison between them is
what isolates what the model's unparsable output contributes to the analyst's bundle, and neither
run alone shows it. Preserved as \texttt{judge\_contribution\_uncapped.*} and \texttt{judge\_contribution\_capped.*}.

\textbf{Figures are generated from the same retained records as the text.} The script recomputes intervals
with the seeded bootstrap rather than reading them out of a summary, so a figure and a sentence
cannot drift apart without the script failing to reproduce one of them. This caught a live error. An
ROC computed by naive descending sort returned AUC \fact{confidence-auc-naive-legacy} against the \fact{confidence-auc} in our text, because
\fact{confidence-modal-count} of \fact{confidence-n} claims are tied at confidence \setting{1.0} and tie handling decides the entire estimate. The text was
right and the first draft of the figure was wrong, which is the ordinary direction for this check to
fire, and the reason for wiring it this way.

Three harness properties are deliberate and worth copying. Every sweep restarts the server it
depends on between samples, because a read timeout leaves the Ghidra JVM mid-analysis and every
subsequent load is refused, and a whole window of samples was lost to this before it was understood.
Every sweep reports how many distinct outputs the N inputs produced, because that one line is the
cheapest detector for the stale-state defects described in Threats to Validity. And every sweep
records the host's memory state at both ends of each unit of work, so that a failed unit can
afterwards be attributed to the pipeline or excluded as an artefact of the machine, a question that
cannot be reopened later, as Section~3 above describes.
