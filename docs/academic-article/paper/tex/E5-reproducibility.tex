\subsection{The engine, and an honest note about how we know}\label{the-engine-and-an-honest-note-about-how-we-know}

Engine: \texttt{ik\_llama.cpp}, commit \textbf{\texttt{eb570eb96689c235933b813693ca28ab9d3d26de}}
(\emph{``MTP: Avoid per step SSM copy (\#1778)''}).

\textbf{The binary could not identify itself.} \texttt{llama-server\ -\/-version} prints \texttt{version:\ 0\ (unknown)},
because the build tree was never a git checkout. The commit was recovered from a depth-1 clone
vendored elsewhere in the project and then \emph{proved} to describe the build: identical 837-file source
lists, and with line endings normalised \textbf{exactly one file differs --- the generated
\texttt{common/build-info.cpp}}.

We report the reconstruction rather than presenting the identifier as though it had been recorded.
The transferable lesson is the one we learned the hard way: \textbf{build provenance must be captured at
build time.} A retracted first version of this row concluded the commit was unrecoverable; it was
recovered only because a vendored copy happened to exist.

\subsection{Hardware, and the ceiling it imposes}\label{hardware-and-the-ceiling-it-imposes}

Single host: RTX 5060, 31 GiB RAM, 16 threads. Three measured properties that shape what can be
reproduced here:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{llama-server} grows with cumulative requests and does not plateau} --- 10.4 GB fresh, \fact{llama-rss-growth-gb} GB
  after a single full analyst pass. A long paired run must restart it between arms; at temperature 0
  this is measurement-neutral.
\item
  \textbf{Serving at 64k instead of \fact{fallback-bundle-total}k does not lower the peak} (14.6 vs \fact{llama-rss-growth-gb} GB) --- the baseline is
  CPU-resident expert weights, and the growth follows the context a pass actually consumes.
\item
  \textbf{Generation rate varies from 162 to 20 tokens/s across requests.} On this hybrid recurrent
  architecture, llama.cpp writes and erases a \textbf{63 MiB recurrent-state checkpoint every few hundred
  tokens} at \textasciitilde39k tokens of context. Long-context calls are therefore not slow in proportion ---
  they fall off a cliff.
\end{itemize}

The Ghidra container is capped at \textbf{6 GB} (\texttt{mem\_limit}). Its JVM \texttt{-Xmx4g} bounds the heap only;
the database is memory-mapped and measured RSS reached 5.15 GB against that nominal 4 GB cap. Two
host lock-ups preceded this limit being added.

\textbf{The working set does not fit alongside an interactive session, and that is a reproducibility fact
rather than an operational one.} Model server \textasciitilde16 GB, analysis worker \textasciitilde8 GB, disassembly container
up to 6 GB: on a 31 GiB host this leaves nothing for a desktop. When we ran a paired study without
that headroom, the swap file was exhausted, the model server had \textbf{2.3 GB of its own address space
paged out}, and one arm then exceeded a \fact{salvage-budget-seconds}-second budget on a \fact{static-max-chars}-character prompt. A model
generating from disk-backed pages is a different instrument from one generating from RAM, and the
timings it produces are not comparable to the rest of the table.

Two consequences for anyone reproducing this work:

\begin{itemize}
\item
  \textbf{Give the run the machine.} Long paired studies here are run against an otherwise-idle host. This
  is not a performance recommendation; arms measured under memory pressure are not commensurable with
  arms that were not.
\item
  \textbf{Record the host state per arm, not per study.} Our harnesses capture \texttt{MemAvailable}, \texttt{SwapFree}
  and the model server's resident-versus-swapped split at both ends of every arm, and the scoring
  script excludes arms whose host was degraded. This screen can only be applied forward: for arms
  already collected without it, the state is gone and the honest label is \texttt{unattributable}. That is
  the label our own halted ablation carries.
\item
  \textbf{Start the model server in its own cgroup, not the harness's.} This one cost us three
  interrupted runs before we read the kernel log carefully enough:

\begin{verbatim}
task_memcg=/user.slice/.../snap.code.code-*.scope, task=llama-server
Out of memory: Killed process (llama-server) oom_score_adj:1000
snap.code.code-*.scope: Failed with result 'oom-kill'
\end{verbatim}

  The harness had launched the server as a child process, so it inherited the cgroup of whatever
  started the harness --- an editor's integrated terminal --- and its \textasciitilde16 GB was accounted to the
  editor's scope. We had already made the server the kernel's preferred victim, and that was the
  wrong level: choosing \emph{which process} dies cannot change \emph{whose accounting it dies inside}.
  Launching it as a transient unit with an explicit \texttt{MemoryMax} puts the measurement's memory where
  it belongs and lets the server hit a limit of its own before the host has to arbitrate.
\end{itemize}

\subsection{The sandbox, and three things that will block a reader}\label{the-sandbox-and-three-things-that-will-block-a-reader}

CAPE 2.5 at a private address, reachable only from one network.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{One analysis machine} (\texttt{win10}, x64), no Linux VM. Only Windows PE can be analysed dynamically
  whatever the code's stated scope, which is why the cohort is Windows-only. An ELF submitted there
  joins the 10,348 tasks that are never scheduled.
\item
  \textbf{Reports are retained for days, not indefinitely.} Sampled across the full task-id range, \textbf{18
  of 18} older tasks return \texttt{"Reports\ directory\ does\ not\ exist"}; a report from four days earlier
  survived. The local archive of fetched reports is therefore \textbf{the only copy}, and ``submit the
  same samples'' is not a reproduction recipe on its own.
\item
  \textbf{The instance rate-limits, and its throttle response is byte-identical to its auth refusal} ---
  \texttt{\{"error":\ true,\ "message":\ ""\}} in both cases. A harness that reads that string as a capability
  verdict will mis-classify a throttle as a missing permission; we did, briefly. Re-call a tool that
  worked minutes earlier to tell them apart.
\end{enumerate}

Timing, for planning: a new Windows submission is scheduled in \textbf{\textasciitilde1 second} and completes in
\textbf{\textasciitilde5.5 minutes}; the 10,348-task backlog is never scheduled and does not queue ahead of new work.
An n=100 cohort is roughly 9 hours of sandbox time.

\textbf{\texttt{enable\_thinking} is honoured on DashScope and ignored on OpenRouter.} Not rejected --- accepted,
recorded in the result file, and not acted on: the re-run requesting it returned a \textbf{56.2\%}
reasoning share against \textbf{56.5\%} without it. On DashScope the same request produces \textbf{0.0\%}. This
is the single most important line in this appendix for anyone comparing arms, because the flag is
worth 0.34--0.45 F1 on the two models where it can be set, and an arm can therefore be labelled
matched while running the opposite configuration. \texttt{eval\_parameter\_size\_series.py} selects arms on
the \textbf{measured} reasoning share for exactly this reason and refuses to correlate when fewer than
three configuration-matched arms span three parameter counts --- which, on these endpoints, is
always.

\textbf{The local server's output cap must be sent twice.} \texttt{ChatOpenAI(max\_tokens=N)} reaches the wire as
\texttt{max\_completion\_tokens}, which \texttt{ik\_llama.cpp} does not read; the cap must also travel in
\texttt{extra\_body} as \texttt{max\_tokens} and \texttt{n\_predict}. Measured on this host: \fact{cap-requested} requested, \textbf{\fact{cap-ignored-tokens}
generated} with the renamed field alone, \textbf{\fact{cap-honoured-tokens}} with both. A reader who omits this will find the
verdict model decoding to the context limit, which is what happened here for as long as the cap had
existed. \texttt{probe\_outbound\_parameters.py} re-checks this and the other outbound parameters against a
running server; it is the regression witness, and it is cheap enough to run before any measurement
campaign.

Note also that this server \textbf{truncates silently}: at the cap it returns \texttt{finish\_reason:\ "stop"},
never \texttt{"length"}, and carries no \texttt{stopped\_limit} field. Telemetry that detects truncation by finish
reason will report zero however often the cap binds; compare the generated-token count against the
cap that was requested instead.

\subsubsection{The original frontier arm}\label{the-original-frontier-arm}

OpenRouter, \texttt{nvidia/nemotron-3-super-120b-a12b:free}, temperature 0, \fact{consensus-budget}-token output cap.

\textbf{The free tier allows 50 requests per day} (\texttt{X-RateLimit-Limit:\ 50},
\texttt{limit\_source:\ openrouter\_free\_tier\_daily}), resetting daily, with a 20-requests-per-minute cap
that applies whether or not credit has been purchased. The \textbf{first} attempt at this arm exhausted
the daily quota mid-flight --- 9 calls landing and 16 returning HTTP 429 --- and the n=9 estimate it
produced was not merely imprecise but pointed the wrong way (§2). The arm reported above is the
completed \textbf{n=25} run, taken from a fresh quota: 25 of 25 parsed, 0 refusals, \$0 charged against
the \$25 ceiling.

The quota is stated here because it governs what a cohort-scale frontier arm costs in wall-clock
rather than in dollars: one call per sample over a \fact{baseline-n}-sample cohort is two days at 50 requests per
day, and a full-pipeline arm --- roughly 20 model requests per analysis --- is not reachable on the
free tier at all. The spend meter is enforced as a precondition on every call rather than reconciled
afterwards, and projections price output at the full cap because a degenerate decode produces
exactly that.

Two of these exist only because a result could not be believed, and both are worth running before
the studies they check rather than after. \texttt{verify\_b3\_mechanism.py} recomputes each ablation arm's
cascade set from its seeded fixture and compares it against what the arm recorded --- it is what
established that a published finding of ours had measured a post-processing step rather than a
model. \texttt{probe\_outbound\_parameters.py} asks whether the server acts on each parameter we send it,
by behaviour rather than by reading a response field, because a server that ignores a parameter
does not report having done so.

The judge-contribution study is run \textbf{twice, in two conditions}, and the pair is kept: once with
the output cap not reaching the server and once with it binding. The comparison between them is
what isolates what the model's unparsable output contributes to the analyst's bundle, and neither
run alone shows it. Preserved as \texttt{judge\_contribution\_uncapped.*} and \texttt{judge\_contribution\_capped.*}.

\textbf{Figures are generated from the same retained records as the text.} The script recomputes intervals
with the seeded bootstrap rather than reading them out of a summary, so a figure and a sentence
cannot drift apart without the script failing to reproduce one of them. This caught a live error: an
ROC computed by naive descending sort returned AUC 0.458 against the \fact{confidence-auc} in our text, because 186
of 210 claims are tied at confidence 1.0 and tie handling decides the entire estimate. The text was
right and the first draft of the figure was wrong --- which is the ordinary direction for this check to
fire, and the reason for wiring it this way.

Three harness properties are deliberate and worth copying. Every sweep \textbf{restarts the server it
depends on between samples}, because a read timeout leaves the Ghidra JVM mid-analysis and every
subsequent load is refused --- a whole window of samples was lost to this before it was understood.
Every sweep reports \textbf{how many distinct outputs the N inputs produced}, because that one line is the
cheapest detector for the stale-state defects described in Threats to Validity. And every sweep
records the \textbf{host's memory state at both ends of each unit of work}, so that a failed unit can
afterwards be attributed to the pipeline or excluded as an artefact of the machine --- a question that
cannot be reopened later, as §3 above describes.
