# LLM Agents for Binary Reverse Engineering and Malware Analysis: A Literature Review with Gap Analysis

## TL;DR
- **The agentic, tool-driving binary-RE literature is dominated by frontier cloud models (ClearAgent, the COTS-binaries agent on GPT-5.4/Opus 4.6, TTPDetect on Claude 3.7); small open-weight models appear almost exclusively as *fine-tuned single-shot specialists* (ReCopilot on Qwen2.5-Coder-7B, LLM4Decompile, Nova, MALSIGHT) rather than as the reasoning engine of a Ghidra/IDA tool loop. No peer-reviewed study evaluates a small (≤~8B) local open-weight model as a *tool-driving* binary-RE agent — the exact configuration in "Our position."**
- **Tool-selection degradation as a function of catalogue size is well documented in the *general* agent literature (LongFuncEval reports a 7.59%–85.58% drop; Less-is-More shows an 8B model flips from failure to success when a 46-tool catalogue is cut to 19) but has never been measured for a reverse-engineering tool catalogue. No paper formalizes which RE sub-tasks should be delegated to the model vs executed deterministically.**
- **The "Our position" system (a ~3B MoE local model, a curated 20-tool allowlist, high-value tools invoked deterministically from code) targets all three gaps directly and would be a genuine contribution — but as stated it rests on a single feasibility datapoint (~201 tools ≈ 22k tokens is infeasible) rather than a degradation *curve*, offers no delegation-boundary ablation, no static-allowlist-vs-dynamic-retrieval comparison, and no local-vs-cloud head-to-head. Those are the measurements needed to make the claims convincing.**

---

## Key Findings

1. **The field is not GPT-4-only, but the *local-agentic* combination is a genuine hole.** Small open-weight models are the norm among fine-tuned binary specialists, and open-weight models are routinely benchmarked (BinMetric tests Llama2, CodeLlama, DeepSeek, WizardCoder, Mixtral). But every peer-reviewed *agentic* system that drives a decompiler through a tool interface uses a frontier cloud model. The only local-agentic evidence is non-peer-reviewed (Cisco Talos's Devstral:24b blog; LLNL's OGhidra).

2. **Catalogue-size degradation is quantified generally, never for RE.** LongFuncEval, Less-is-More, CarbonCall and Anthropic's own engineering data all show tool-selection accuracy collapses as the catalogue grows, and Anthropic states the effect begins at 30–50 tools. No one has run this ablation on a Ghidra/IDA MCP catalogue, where schemas are large (~201 tools ≈ 22k tokens) and tools semantically overlap.

3. **The delegation question is embodied but never formalized.** LAMD and TTPDetect both do deterministic pre-processing (slicing, retrieval) and reserve the LLM for semantic reasoning, and the UW-Madison survey argues for deterministic tokenization/deobfuscation — but no study ablates the boundary of *which* sub-tasks belong to the model.

4. **A common citation error to avoid:** the widely repeated "43%→2% as tools grow from 4 to 51" statistic is from a LangChain engineering blog, not the Berkeley Function Calling Leaderboard.

## Details

### Question 1 — State-of-the-art systems: architecture-by-architecture

The literature separates into four families. For each system I note what the LLM decides vs what is deterministic, model locality, tool interface, and evaluation.

**A. Agentic systems driving a decompiler backend (MCP / function calling).**

- **ClearAgent** — Xiang Chen, Anshunkang Zhou, Chengfeng Ye, Charles Zhang (HKUST), "ClearAgent: Agentic Binary Analysis for Effective Vulnerability Detection," *Proceedings of the 1st ACM SIGPLAN International Workshop on Language Models and Programming Languages (LMPL '25)*, pp. 130–137, **DOI 10.1145/3759425.3763397**. The LLM chooses among "principled strategies" (DFS vs BFS, backward vs forward) and a phased top-level strategy; a Context Manager governs exploration; deterministic backends verify candidate bugs by constructing concrete triggering inputs. Cloud model. Evaluation: CWE-typed vulnerability detection.
- **"Agentic Vulnerability Reasoning on COTS Binaries"** — **arXiv 2605.05000** (2026 preprint, venue UNCERTAIN). ReAct loop plus binary-analysis/debugging tools targeting Windows COM vulnerabilities. Per my targeted follow-up, it evaluates six frontier backbones (e.g., GPT-5.4, Opus 4.6), reporting 23/40 and 27/40 PoC success and 28 previously unknown vulnerabilities with 16 CVEs; **exact figures UNCERTAIN**. Cloud models only — a counter-example to the local-model direction.
- **TTPDetect** — Zhou Xuan et al. (Purdue), "Identifying Adversary Tactics and Techniques in Malware Binaries with an LLM Agent," **arXiv 2602.06325** (2026 preprint). First LLM agent for MITRE ATT&CK TTP recognition in *stripped* malware binaries. Dense retrieval + LLM-based neural retrieval narrows entry points (deterministic); a function-level agent with a "Context Explorer" does incremental on-demand context retrieval; a TTP-Specific Reasoning Guideline performs inference-time alignment. Reports 93.25% precision / 93.81% recall at function-level TTP recognition, +10.38 / +18.78 points over baselines. Example outputs use Claude 3.7 Sonnet (cloud).
- **Open-source practitioner agents** (engineering artifacts, not peer-reviewed evaluations): GhidraMCP (LaurieWired) exposes Ghidra APIs over MCP; ReVa/reverse-engineering-assistant (cyberkaida) deliberately returns small critical fragments with cross-references to limit context and hallucination; OGhidra (LLNL, github.com/llnl/OGhidra) runs a Plan→Execute→Review→Replan loop over Ollama models with budget-aware context compression; GhidrAssist (jtang613) supports local models with an agentic mode. Ghidra MCP servers now expose very large catalogues — public repos advertise 179–200+ tools; pyghidra-mcp explicitly keeps the surface narrow "so agent clients spend fewer tokens on tool discovery," corroborating the ~201-tool figure in "Our position."

**B. Fine-tuned binary-specialist models (the LLM *is* the analysis engine; a deterministic decompiler feeds it).**

- **ReCopilot** — Guoqiang Chen et al. (XingTu Lab / QI-ANXIN), **arXiv 2505.16366**. Expert LLM built on **Qwen2.5-Coder-7B** via continued pre-training + SFT + DPO, with data-flow and call-graph context enhancement and test-time scaling. Tasks on decompiled pseudo-C: function name recovery, variable name/type inference, struct recovery, binary code summarization, decompilation. Benchmark: 1,038 functions from 60 binaries, IDA Pro 9.0 runtime. The paper reports the model "outperforms the existing domain models by 13% averaged across tasks," an average score exceeding Qwen2.5-Coder-7B-Instruct "by 14%," and a "small advantage of 5%" over DeepSeek-R1 — including a ~71% relative lead on variable-name recovery (50.59/43.50 vs DeepSeek-R1's 43.63/25.36). This is the cleanest example of a *small, local, open-weight* (7B) model as the analysis engine, though it is a single-shot predictor, not a tool-driving agent.
- **LLM4Decompile** — Hanzhuo Tan, Qi Luo, Jing Li, Yuqun Zhang, EMNLP 2024, **DOI 10.18653/v1/2024.emnlp-main.203** (S&P 2024 version **DOI 10.1109/SP54263.2024.00152**; **arXiv 2403.05286**). First open-source LLM series for decompilation (End and Ref variants; 1.3B/6.7B/33B). Crucially for the malware-hardness discussion, the paper documents that decompilation success "significantly drop[s] for over 70%" under obfuscation — the re-executability rate of LLM4Decompile-Ref-6.7B falls 90.2% (0.5274→0.0519) under control-flow flattening and 78.0% (0.5274→0.1159) under bogus control flow.
- **Nova** — Nan Jiang et al., **arXiv 2311.13721**, ICLR 2025. Generative foundation LLM for assembly (1.3B / 6.7B) built on DeepSeek-Coder with hierarchical attention and contrastive learning, "achieving 14.84–21.58% absolute gains in Pass@1 and Pass@10" over LLM4Decompile on HumanEval-Decompile; Nova-1B beats GPT-4o by 8.38 Pass@1. Open-weight.
- **MALSIGHT / MalT5** — Haolang Lu et al., **arXiv 2406.18379** (IEEE Xplore doc 11052730). Fine-tunes CodeT5+ for iterative binary malware summarization; introduces MalS/MalP datasets and the BLEURT-sum metric. Small open-weight.

**C. Prompt-only pipelines over decompiled pseudo-C (no agentic tool loop).**

- **LAMD** — Xingzhi Qian et al., **arXiv 2502.13055** (IEEE doc 11050830). Android/Dalvik but methodologically central: deterministic backward slicing extracts key context, then *tier-wise* LLM reasoning (function→API→APK) with factual-consistency verification, evaluated on GPT-4o-mini. Exemplar of the "deterministic pre-processing, LLM at higher tiers" division.
- **Multi-View Decompilation for LLM-Based Malware Classification** — **arXiv 2606.20436**. Pairs Ghidra + RetDec pseudo-C views; argues single-decompiler pipelines are fragile.
- **A Decompilation-Driven Framework for Malware Detection** — Aniesh Chawla, Udbhav Prasad, **arXiv 2601.09035**. Ghidra→C→LLM classification; a fine-tuned model beats vanilla but degrades on newer malware.
- **Exploring the Efficacy of GPT-4 in Binary Reverse Engineering** — Saman Pordanesh, Benjamin Tan, **arXiv 2406.06637**.
- **Deobfuscation** — "Deconstructing Obfuscation: A four-dimensional framework…" **arXiv 2505.19887**; Patsakis, Casino, Lykousas, "Assessing LLMs in malicious code deobfuscation of real-world malware campaigns," *Expert Systems with Applications* 256:124912, 2024.

**D. Dynamic / sandbox-trace agents.**

- **ABLE** — **arXiv 2605.21821**. LLM analyzes execution traces from evasive malware and generates YARA bypass rules with auto-sanitization and feedback-driven sandbox re-execution (CAPE-compatible). The LLM decides bypass rules; the sandbox and behavioral validator are deterministic. Underlying model class **UNCERTAIN**.
- **RAG + Threat Intelligence pipeline** — "Leveraging LLMs to Support Malware Analysis from Structured and Semantic Binary Data," Springer, **DOI 10.1007/978-981-92-0263-8_35**. Static (PE/strings/API) + dynamic (sandbox logs) → MITRE ATT&CK mapping + APT attribution with RAG over ThreatFox.

**Benchmarks / evaluation infrastructure.** BinMetric (Xiuwei Shang et al., **arXiv 2505.07360**; **IJCAI 2025 paper #858**) — 1,000 questions, 20 projects, 6 tasks, 12 LLMs. BinSum (Xin Jin et al., **arXiv 2312.09601**) — 557K functions, multi-modal. REBench (**arXiv 2604.27319**, venue UNCERTAIN) — procedural, fair-by-construction stripped-binary types/names. REFORGE (**arXiv 2607.07738**) — provenance-tracked function-naming benchmark documenting survivorship bias. AgentRE-Bench (agentre-bench.ai) — deterministic scoring on stripped ELF, 13 levels, 25 tool-call budget (non-peer-reviewed). CTF-oriented: NYU CTF Bench, EnIGMA (**arXiv 2409.16165**), CTF-Dojo (**arXiv 2508.18370**), CRAKEN (**arXiv 2505.17107**).

**Survey anchor.** Radey, West, Fawaz (UW-Madison), "Challenges and Future Directions in Agentic Reverse Engineering Systems," **arXiv 2604.14317** — taxonomizes static/dynamic/hybrid agents and catalogues six limitations (obfuscation, tokenization/context, lack of dynamic-analysis guardrails, timeouts, emulation reliance, unbounded reasoning). It observes that "no agent focuses on dynamic analysis" alone and that hybrid systems either rely on a human-in-the-loop or reason entirely internally.

### Question 2 — What is missing

**(a) Local, small, open-weight models.** Fine-tuned specialists are overwhelmingly small open-weight (ReCopilot 7B; LLM4Decompile 1.3–33B; Nova 1.3/6.7B; MALSIGHT/CodeT5+). BinMetric (arXiv 2505.07360) benchmarks Llama2-7B, CodeLlama-7B/34B, DeepSeek-7B, DeepSeek-Coder-7B/33B, WizardCoder-15B/33B and Mistral/Mixtral, and finds them trailing GPT-4 (open-source mean 22.93% vs closed 27.46%; algorithm-classification accuracy GPT-4 83.75% vs Llama2-7B 15%). **But in the *agentic, tool-driving* setting that defines this review's scope, the backbone is almost always a frontier cloud model** (ClearAgent; COTS-binaries agent on GPT-5.4/Opus 4.6; TTPDetect on Claude 3.7). The only local-model agentic evidence I found is non-peer-reviewed: the Cisco Talos "reverse-engineering sidekick" writeup (Devstral:24b via Ollama driving Ghidra/IDA MCP), which documents that the local model "kept 'forgetting' its instructions and stopping analysis after only a dozen functions," and LLNL's OGhidra. **Conclusion: I found no peer-reviewed, systematic evaluation of a small (≤~8B) local open-weight model as the reasoning engine of a tool-driving binary-RE agent.** This is "no work found in my search," not proof of non-existence.

**(b) Tool-selection degradation vs catalogue size.** Well established generally, absent in RE:
- **LongFuncEval** (Kate, Pedapati, Basu, Rizk, Chenthamarakshan, Chaudhury, Agarwal, Abdelaziz — IBM et al., **arXiv 2505.10570**, submitted 30 Apr 2025, cs.SE) is the strongest primary source, identifying "three predominant challenges: (1) a large catalog of tools, (2) long responses from the tool APIs, and (3) long multi-turn conversations," and measuring a **7.59%–85.58%** accuracy drop as the tool catalogue grows from 8K to 120K tokens. It explicitly states that no prior study "systematically documented the impact of tool catalog size on tool calling performance of LLMs."
- **Less-is-More** (**arXiv 2411.15399**): on edge, Llama3.1-8b-q4 fails to select the correct tool from GeoEngine's 46-tool set even within a 16K window, but succeeds when the set is cut to 19 tools; execution time falls up to 70% and power up to 40%.
- **CarbonCall** (**arXiv 2504.20348**): dynamic tool selection via vector search + re-ranking; cite for mechanism/motivation, not for a clean accuracy-vs-N curve.
- **Anthropic Engineering** ("Introducing advanced tool use on the Claude Developer Platform"): "58 tools consuming approximately 55K tokens before the conversation even starts... we've seen tool definitions consume 134K tokens before optimization." Its Tool Search Tool preserved 191,300 vs 122,800 tokens of context (~85% reduction) and lifted Opus 4 accuracy "from 49% to 74%"; independent summaries note Claude's tool-selection "degrades significantly past 30 to 50 tools."
- **Berkeley Function Calling Leaderboard** (Patil/Yan et al., ICML 2025) confirms the trend but is not a controlled N-sweep. **The "43%→2% as tools go 4→51" figure comes from a LangChain engineering blog, not BFCL** — a frequent misattribution.

**No paper measures tool-selection degradation for a reverse-engineering tool catalogue** (Ghidra/IDA MCP), where the catalogue is large (~201 tools) and tools semantically overlap. The RE survey (arXiv 2604.14317) flags token/context constraints but runs no catalogue-size ablation.

**(c) Which sub-tasks to delegate vs execute deterministically.** Only implicit. The UW-Madison survey (arXiv 2604.14317) argues for deterministic byte-pattern tokenization, deobfuscation, and stripping stack-frame boilerplate, but gives no principled delegation boundary. LAMD (arXiv 2502.13055) and TTPDetect (arXiv 2602.06325) embody the "deterministic slicing/retrieval + LLM semantic reasoning" pattern without ablating it. "LLM Agent-Assisted Reverse Engineering with Quantitative Readability Metrics" (arXiv 2606.06838) documents agentic failure modes — context rot, metric gamification, functional regressions — that motivate keeping high-value operations deterministic, but again does not formalize the boundary. **No systematic study answers "which RE sub-tasks belong to the model vs deterministic code."**

**Adjacent gap — adversarial robustness.** Prompt injection via binary strings is small but emerging: "Automatically Attacking Software Reverse Engineering AI Agents" (**arXiv 2605.30667**, AutoDAN-style injection through string variables, ECCWS) and "Investigating Detection and Obfuscation of Prompt Injection Attacks Against Software Reverse Engineering AI Agents" (**arXiv 2605.30677**, Naval Postgraduate School). Both note GhidraMCP's 2048-character decompiler truncation as an incidental mitigation.

### Question 3 — Does "Our position" address the gaps? Where does it fall short?

The described system — a small **local** open-weight model (~3B active MoE) driving Ghidra through a curated 20-tool allowlist, with high-value tools invoked deterministically from code, motivated by the measurement that the full ~201-tool catalogue (~22k tokens of schema) is infeasible for a model this size — maps onto all three gaps.

**Where it directly addresses gaps:**
1. **Gap (a).** A ~3B MoE *tool-driving* agent is precisely the under-studied configuration. ReCopilot (7B) is the closest peer but is a fine-tuned single-shot predictor, not an agent; the only local-agentic precedents (Talos Devstral:24b, OGhidra) are non-peer-reviewed and ≥24B. A ~3B agentic evaluation would be a genuine first.
2. **Gap (b).** The ~201-tools ≈ 22k-tokens infeasibility measurement, motivating a 20-tool allowlist, is exactly the RE-domain instantiation of LongFuncEval/Less-is-More that no one has published. Less-is-More's 46→19 result on an 8B model strongly predicts the effect replicates and worsens at 3B, and Anthropic's "degrades past 30–50 tools" observation is consistent.
3. **Gap (c).** Invoking high-value tools deterministically from code rather than exposing them to the model is a concrete delegation policy that operationalizes the survey's implicit recommendation.

**Where it falls short / is not yet convincing:**
- The claim rests (as stated) on a single feasibility datapoint, not a *curve*; the field's value has been in the degradation function, not a single threshold.
- 20 vs 201 is a binary comparison — no evidence about the intermediate regime, the optimal allowlist size, or whether retrieval-based dynamic tool selection (CarbonCall; RAG-MCP, arXiv 2505.03275) would beat a static allowlist.
- "High-value tools invoked deterministically" needs an explicit, justified taxonomy of which tasks are delegated and why; otherwise it is an engineering choice, not a measured finding (Gap c stays open).
- No head-to-head against a cloud frontier agent on the same binaries, so the accuracy cost of going local is unquantified.
- Adversarial robustness (arXiv 2605.30667 / 2605.30677) is unaddressed; a deterministic allowlist reduces but does not eliminate the string-injection surface.
- Malware-specific hardness — stripped, obfuscated, packed samples — is where agents demonstrably degrade (arXiv 2604.14317; LLM4Decompile shows a 90.2% re-executability drop under control-flow flattening). The position statement does not indicate whether evaluation covers this.

### Question 4 — What must be built or measured to close the gaps convincingly

1. **A catalogue-size degradation curve for the RE domain.** Measure task success and tool-selection accuracy as the exposed Ghidra/IDA MCP catalogue grows (e.g., 5 → 20 → 50 → 100 → 201 tools) on a fixed binary set, for the 3B MoE plus at least one mid-size and one frontier model. This directly extends LongFuncEval (arXiv 2505.10570) and Less-is-More (arXiv 2411.15399) into binary RE, where no such curve exists.
2. **A delegation ablation.** For each RE sub-task (decompilation retrieval, xref enumeration, renaming, type/struct recovery, string/import triage, control-flow summarization, TTP mapping), compare LLM-delegated vs deterministic-from-code execution on accuracy, latency, token cost, and hallucination rate — producing an evidence-based delegation boundary (closing Gap c).
3. **Static allowlist vs dynamic retrieval.** Benchmark the 20-tool allowlist against retrieval/RAG-based dynamic tool selection (CarbonCall arXiv 2504.20348; RAG-MCP arXiv 2505.03275) and Anthropic-style tool search, to show the allowlist is not merely simpler but competitive or better at 3B.
4. **Local-vs-cloud head-to-head on shared benchmarks.** Run the 3B-MoE agent and a frontier agent on BinMetric (arXiv 2505.07360), a stripped-binary naming/type benchmark (REBench arXiv 2604.27319 / REFORGE arXiv 2607.07738), and a TTP set (TTPDetect-style, arXiv 2602.06325), reporting the accuracy gap and the cost/privacy advantage of local.
5. **Real-world malware hardness.** Evaluate on stripped, obfuscated, and packed samples; report degradation under control-flow flattening and bogus control flow (per LLM4Decompile arXiv 2403.05286 and the survey arXiv 2604.14317).
6. **Adversarial robustness.** Test against string-injection attacks (arXiv 2605.30667 / 2605.30677) and report whether the allowlist plus code-invoked high-value tools shrink the attack surface.
7. **Reproducibility harness.** Fixed binaries, deterministic scoring (as AgentRE-Bench and REFORGE advocate), explicit tool-call budgets, and released traces so the local-model claims are auditable.

## Recommendations

- **Stage 1 (frame the contribution around the two clean gaps).** Position the paper primarily as (i) the first RE-domain tool-catalogue degradation study and (ii) the first small-local-open-weight *agentic* binary-RE evaluation. These are defensible "no work found" gaps. Lead with the degradation curve (Recommendation 1 above) because it is the most novel and the easiest to make rigorous; a curve showing 3B collapse between ~20 and ~201 tools, contrasted with an 8B/70B/frontier model, would be a headline result. **Threshold that would change this:** if a search of the final camera-ready cycle surfaces a peer-reviewed local-agentic RE evaluation (watch arXiv 2604.14317's citation graph and LMPL/DIMVA/RAID 2026 proceedings), reframe as a replication-plus-extension rather than a first.
- **Stage 2 (turn the single feasibility datapoint into a curve, and make the allowlist earn its place).** Do not publish "201 tools is infeasible" as a standalone claim — run the sweep and add the static-vs-dynamic-retrieval comparison. **Benchmark that matters:** if dynamic retrieval matches the 20-tool allowlist within noise, the allowlist's justification becomes simplicity/auditability, not accuracy, and the paper should say so explicitly.
- **Stage 3 (formalize delegation).** Publish the delegation taxonomy with the ablation in Recommendation 2; this converts an engineering decision into a measured finding and is the most citable conceptual contribution.
- **Stage 4 (harden and contextualize).** Add the local-vs-cloud head-to-head, real-world malware hardness, and the prompt-injection robustness test. **Threshold:** if the local 3B agent trails a frontier agent by more than a task-defined margin on BinMetric-style tasks, pivot the value proposition to privacy, cost, reproducibility, and offline operation (well supported by the local-LLM RE-tooling literature) rather than raw accuracy.
- **Citation hygiene:** attribute the "43%→2%, 4→51 tools" figure to the LangChain blog, not BFCL; cite CarbonCall for mechanism only; and flag every 2026 arXiv preprint (2605.05000, 2602.06325, 2606.20436, 2601.09035, 2604.14317, 2604.27319, 2607.07738, 2605.21821, 2605.30667, 2605.30677) as not-yet-formally-published.

## Caveats

- **Recency and venue.** Much of the most relevant work is 2025–2026 arXiv preprints whose final peer-reviewed venues are UNCERTAIN. I verified their contents from fetched text/snippets but could not confirm acceptance for the 2026 IDs listed above.
- **Model class gaps.** ABLE's (arXiv 2605.21821) underlying model class could not be confirmed. The COTS-binaries agent's (arXiv 2605.05000) exact success figures and model versions are from a single follow-up read and should be re-verified against the PDF.
- **Attribution correction.** The "43%→2% when tools expand from 4 to 51" statistic is from a LangChain engineering blog (industry, non-peer-reviewed), not the Berkeley Function Calling Leaderboard.
- **Search-limited negative claims.** "No peer-reviewed evaluation of a small local open-weight model as a tool-driving binary-RE agent" and "no RE-domain catalogue-size degradation study" and "no formal RE delegation-boundary study" are all based on my searches; they are strong signals of a real gap but are not proofs of non-existence. A dedicated query of DIMVA/RAID/ACSAC 2026 and the citation graphs of arXiv 2604.14317 and 2505.10570 should precede any absolute claim in the final paper.
- **Practitioner tooling vs science.** Several local-model RE systems (OGhidra, GhidrAssist, GhidraMCP, Talos's Devstral setup) exist as engineering artifacts without controlled evaluations; they demonstrate feasibility but do not close the measurement gaps.
