## Findings, by component

### W-01 (CRITICAL, fixed in session) — worker process env had `MALJAN_MOCK_MODE=true`

**Evidence.** Inspected the running arq processes with `psutil.Process.environ()`:

```
PID=644  MALJAN_MOCK_MODE=true
PID=2204 MALJAN_MOCK_MODE=true
PID=17072 MALJAN_MOCK_MODE=true
PID=20088 MALJAN_MOCK_MODE=true
```

Process tree: `claude.exe → bash.exe → bash.exe → uv.exe (2204) → arq.exe (17072) → python (644) → python (20088)`. The bash that spawned `uv run arq …` had MALJAN_MOCK_MODE exported, so every job picked up `mock=True` via `os.environ.get("MALJAN_MOCK_MODE", "false")` in [analysis_worker.py:166](apps/api/app/worker/analysis_worker.py#L166).

**Symptom.** API jobs `21e4f37d-…` (run #1) and `b2226b0d-…` (run #2) completed in 1.5 s and 0.5 s respectively. Both produced the same fallback report: `verdict=Malware, confidence=0.95`, `executive_summary="… no LLM available …"`, `dynamic=None`, `network=None`, `ttp_mappings=[]`, `negotiation_summary.rounds_completed=0`, `termination_reason="unknown"`. Zero LLM calls reached llama-server during run #2 even though it was healthy.

**Fix (applied in this session).**
1. Identified the four arq processes carrying the mock env var.
2. Killed them with `psutil.Process.terminate()` after explicit user confirmation.
3. Started a fresh worker from `apps/api/` with `env -u MALJAN_MOCK_MODE … DEBUG=true uv run arq app.worker.analysis_worker.WorkerSettings`. New worker logs to `d:/tmp/worker_stdout.log`.
4. Reproduced an API job (`ff85bf38-…`) end-to-end. Worker invoked Triage (`260517-spkcxadz3j`) and made real LLM calls — matches CLI behaviour.

**Permanent recommendation.** Move the mock toggle out of process env and into either:
- `config.yaml` (read once at startup, with a clear log line "MOCK MODE ACTIVE" so the operator can see it), or
- a per-job `config.mock_mode` field that is part of the job's POST body. Job-level toggle would also unblock automated testing without leaking into shared infra.

The env-var approach is too easy to set in one shell and forget.

### T-01 (HIGH) — Triage `summary` parser silently drops sample metadata when `sample` is a string

**Evidence.** [triage_client.py:638-645](src/maljan/loaders/triage_client.py#L638):

```python
raw_sample = triage_data.get("sample", {})
if not isinstance(raw_sample, dict):
    logger.warning("TriageClient: task=%s 'sample' field is %s, not dict. Using empty.", task_id, type(raw_sample).__name__)
    raw_sample = {}
sample_meta = raw_sample
sha256 = sample_meta.get("sha256", "")
sample_name = sample_meta.get("name", task_id)
```

In the CLI run the warning fired (`'sample' field is str, not dict`), so `sha256=""`, `sample_name=task_id`, and downstream extraction proceeded with an empty `sample_meta`. That cascaded into `dynamic=None` and `network=None` in the MalwareReport even though Triage *did* detonate the sample.

**Root cause.** Triage's `/v0/samples/{id}/summary` returns `sample` as either:
- a dict (when the sample object has been fully resolved), or
- a string (the bare sha256, when summary is built before resolution).

The parser only handles the dict shape and silently zeroes the string shape.

**Fix.** Two-line change:

```python
if isinstance(raw_sample, str):
    sample_meta = {"sha256": raw_sample}
elif isinstance(raw_sample, dict):
    sample_meta = raw_sample
else:
    logger.warning(...)
    sample_meta = {}
```

Better still — drop `summary` as the canonical source and fetch `/v0/samples/{id}/overview.json` (which always has the full sample dict plus signatures + extracted strings). The codebase already has `fetch_overview()` in the same file (it's wired into `_enrich_from_overview`), so this is consolidation work, not new code.

**Why it matters.** Even when the sample *is* detonated, the rendered MalwareReport shows "_No sandbox dynamic data available._" and "_No network observations available._" — which makes Maljan look broken to the analyst even though it's a parser bug.

### J-01 (HIGH) — Judge bundle has placeholder UUIDs leaking from the LLM prompt

**Evidence.** `d:/tmp/cli_stix.json` contains:

```json
{"type":"malware","id":"malware--12345678-1234-1234-1234-123456789012",...}
{"type":"attack-pattern","id":"attack-pattern--T1497",...}
{"type":"relationship","target_ref":"attack-pattern--T1497",...}
```

`malware--12345678-1234-1234-1234-123456789012` is the example UUID from the structured-output schema description that bled through into the model's response. `attack-pattern--T1497` is **not a STIX 2.1-compliant ID** (the spec requires `<type>--<UUIDv4>`).

**Impact.** Any standards-compliant STIX validator (`stix2-validator`, OpenCTI, MISP-STIX import) will reject this bundle. The `relationship.target_ref` pointers are also broken because they point to `attack-pattern--T1497` which is not a real SDO ID.

**Fix.** In the judge agent's structured-output post-processing, rewrite IDs:
- Reject (or substitute) any object whose `id` matches the prompt placeholder pattern `12345678-1234-1234-1234-123456789012`.
- For attack-pattern IDs, normalize to `attack-pattern--{uuid5(MITRE_NAMESPACE, technique_id)}` so the same technique maps to the same UUID across runs, while still being spec-compliant.

`stix_renderer.py` (extended bundle) already creates real UUIDs for indicators — the problem is specifically in the **base judge bundle** that comes from the verdict-LLM structured output.

### J-02 (HIGH) — Judge bundle contains hallucinated C2 indicator

**Evidence.** Indicator in the bundle:

```json
{"name":"RAT C2 Beacon Pattern",
 "description":"Inferred C2 communication pattern based on RAT category and network analysis placeholders.",
 "pattern":"[domain-name:parent_domain_ref.value = '*.c2-beacon.net']",
 "indicator_types":["malicious-activity"]}
```

The sample never contained `c2-beacon.net`. The judge synthesised this from the inferred RAT category, and the description even spells it out ("…placeholders"). This is exactly the kind of fabrication that erodes trust in CTI tooling — pushed downstream to a SOC, this would generate noisy false-positive alerts.

**Fix options (any one will help; combining is best):**

1. **Strict prompt.** Add to the judge system prompt: *"DO NOT emit indicators (`type=indicator`) whose pattern values do not appear in the deterministic evidence. The `description` field MUST NOT contain words like 'inferred', 'placeholder', or 'example'."*
2. **Post-validation filter.** After parsing the bundle, drop any indicator whose pattern value isn't grep-able in `static.interesting_strings ∪ network.* ∪ sandbox_report.network.*`. Log a warning so analysts know one was filtered.
3. **Schema-level separation.** Have the judge emit only `Malware`, `AttackPattern`, `Relationship` (the verdict shape). Move indicator generation to the deterministic extended-STIX renderer that already pulls real IOCs from `MalwareReport.network/static.interesting_strings`.

Option 3 is the cleanest — keeps the LLM out of IOC manufacturing entirely.

### A-01 (MEDIUM) — Static analyst ReAct loop times out at 180 s

**Evidence.** CLI log:
```
17:42:02 maljan.static  Starting ReAct agent loop with 31 tools...
17:45:32 maljan.static  ERROR ReAct agent failed in thread: TimeoutError ()
17:45:32 maljan         ERROR static analysis failed: static ISR analysis failed:
```

3 min 30 s elapsed. 31 Ghidra tools × the realistic time-per-LLM-round on this hardware (≈30 s prompt-processing + 15-30 s generation per round) ≫ 180 s. The static analyst contributed zero ISR claims.

**Why it didn't break consensus.** The judge mediator log says "no dissent — fast path (single LLM call)" — i.e. with one analyst silent, the other two unanimously voted "Malware" so the mediator skipped the negotiation rounds entirely. Lucky outcome; under a disagreement scenario this would have biased the verdict.

**Fix options:**

1. **Per-agent timeout from config** instead of hardcoded 180 s. Make it `negotiation.agent_timeout_seconds` (default 180, override per agent). Add `static_timeout=600` for ReAct-heavy paths.
2. **Allowlist tool count.** 31 Ghidra tools is too many for one ReAct loop. Curate to 10-12 high-value tools (`list_imports`, `decompile_function`, `list_strings`, `get_function_xrefs`, …) and put the rest behind on-demand "give the agent another budget" branching.
3. **Pre-extract** PE/ELF metadata deterministically (already done in `sample_identity.py` + `pe_extractor.py`) and **inline** it into the static analyst prompt instead of forcing the agent to discover it via tool calls. The analyst then focuses on judgement, not info-gathering.

### E-01 (MEDIUM) — ELF section parser is a one-line stub

**Evidence.** `MalwareReport.static.sections` had a single row:
```
{"name":"(binary)", "va":0, "virtual_size":4915352, "raw_size":4915352, "entropy":5.97, "notes":""}
```

The PE extractor doesn't parse ELF. For an ELF binary we should see the `.text` / `.data` / `.rodata` / `.bss` / `.got` / `.plt` / `.symtab` headers plus per-section entropy. The Go-binary in this sample has identifiable Go runtime sections (`.gopclntab`, `.go.buildinfo`) that would help attribute it.

**Fix.** Add an ELF code path in `pe_extractor.py` (or rename it `binary_extractor.py`) that uses `pyelftools` (already used elsewhere in Maljan? — to check) or the standard `lief` library. Same for Mach-O if APK is ever extended to native libs.

### IOC-01 (MEDIUM) — Auto-extracted "ip" strings are X.509 OID fragments and Go loopback constants

**Evidence.** From `static.interesting_strings`, classified as `kind: ip`:
```
5.4.62.5     ← part of OID 2.5.4.6 (countryName) → "...5,4,62,5..."
5.4.82.5     ← part of OID 2.5.4.8 (stateOrProvinceName)
2.5.4.102    ← OID prefix
120.0.0.0    ← Go MaxByte-style sentinel
1.1.1.1, 1.2.1.1, 1.3.1.1   ← test patterns / Go RIPE/TLD constants
```

These get echoed into the auto-generated YARA rule, the Suricata rules (when network is present), and the STIX indicator list. Half the YARA `$sNN` strings in `Maljan_AutoGen_rat` are useless false-positives.

**Fix.** Tighten the `ip` regex in `network_extractor.py` / `ioc_normalizer.py`:
- Reject octets that are `0` or `255` unless the IP is in a curated public-routing range.
- Reject `1.0.0.0/8`, `127.0.0.0/8`, `0.0.0.0/8`, `255.0.0.0/8`, and the standard reserved blocks unless explicitly opted into.
- Cross-check against OID context (preceding bytes look like ASN.1 length prefix → drop).

### REP-01 (LOW) — STIX `attack-pattern.external_references` is empty

The renderer emits each attack-pattern SDO with `external_references: []` instead of populating the canonical MITRE link:
```json
"external_references": [{"source_name":"mitre-attack","external_id":"T1497","url":"https://attack.mitre.org/techniques/T1497"}]
```

The fallback judge path *does* populate this correctly ([judge_agent.py:619-633](src/maljan/agents/judge_agent.py#L619)), so the bug is specifically in the **structured-output happy path** — the LLM's bundle skips this field, and we don't post-fill it.

### OBS-01 (LOW) — Worker drops original filename when downloading to temp

The worker downloads `samples/f5/f5a76962…` from MinIO to `%TEMP%/f5a76962…` (no extension), then submits to Triage with that filename. Triage uses the extension to pick the VM profile (`zararli.elf` → Linux sandbox, `evil.exe` → Windows, etc.). Without an extension Triage falls back to a generic Linux VM.

**Fix in [analysis_worker.py:214](apps/api/app/worker/analysis_worker.py#L214)**:
```python
ext = Path(sample.original_filename).suffix
temp_path = str(Path(tempfile.gettempdir()) / f"{sample.sha256}{ext}")
```

### TIME-01 (LOW) — host ↔ Postgres clock drift ~9 s

```
host UTC                : Sun May 17 14:31:22 UTC 2026
postgres container UTC  : Sun May 17 14:31:31 UTC 2026
```

`AnalysisJob.created_at` uses `server_default=func.now()` (Postgres clock), `job.started_at = datetime.now(UTC)` uses the host clock ([analysis_worker.py:127](apps/api/app/worker/analysis_worker.py#L127)). Every job ends up with `started_at < created_at`.

**Fix.** Pick one source of truth — easiest is `started_at = func.now()` (i.e. let Postgres stamp via `db.execute(update(AnalysisJob).where(...).values(started_at=func.now()))`). Alternatively trust the host clock and use `default=datetime.now(UTC)` for `created_at` in the model.

## Additional findings from the API run

### CWD-01 (CRITICAL) — Sigma rules path resolves relative to CWD, not project root

**Evidence.** `SigmaLayer: rules directory not found: data\sigma_rules — running without Sigma rules.` The fresh worker was started from `apps/api/`, so `data\sigma_rules` resolved to `apps/api/data/sigma_rules` (doesn't exist). The actual location is `d:/Projects/Maljan/data/sigma_rules/` (2 946 rules).

**Impact.** Sigma layer loads **0** rules. For this sample, that meant losing all 6 corroborating Sigma matches that the CLI run found. The cascade goes from 7 TTPs down to 1 (only YARA T1497). The judge then relies on LTM priors to keep the verdict at "Malware" — but the LTM hit is the same sample's previous run, so this is a **self-amplification feedback loop**: degraded run → degraded LTM entry → degraded next run.

**Fix.** Resolve `data/...` paths via `maljan.core.paths.project_root()` (or similar). The pattern needs to follow [config.py:_find_env_file](src/maljan/core/config.py#L335) which walks up from the source file location — apply the same to:
- `data/sigma_rules`
- `data/yara_ttp_rules.yaml`
- `~/.cache/maljan/attck/enterprise-attack.json` (already absolute — good)
- any other `data/*` reference

Grep for all `data\\` and `data/` literals to find the rest.

### LTM-01 (MEDIUM) — Long-Term Memory enables self-amplification

**Evidence.** The Judge prompt included LTM priors:
```
[1/3] sample_id: f5a7696239b801496743753f8066775f68793e81b5d4eceb15f701950774733d (category: rat)
  Past techniques: T1497, T1006, T1059.001, T1095, T1021.001, T1036.006, T1078.004
```

The CLI run (with full Sigma cascade) stored these 7 TTPs to Qdrant. The next API run (without Sigma cascade) retrieved them and used them as "WEIGHTED PRIORS for TTP selection". This is helpful when past runs are correct — and dangerous when they aren't. A false-positive run pollutes its own future cases.

**Fix.** Two-pronged:
1. **Don't store low-quality runs in LTM.** Skip the `store_case` call when `corroborated_count < 1` or when `static_analyst.status == "failed"`. Quality gate before LTM write.
2. **Filter self-matches.** When retrieving LTM priors for a sample, exclude the same sha256 (`if past.sample_id == current.sample_id: skip`). Already implemented for `attribution.populate_similar_samples` — extend the same filter to the judge prompt's LTM retrieval.

### MED-01 (MEDIUM) — Mediator narrative leaks into the verdict prompt

**Evidence.** When 2 of 3 analysts return empty results because of T-01 + A-01, the mediator's structured output literally states:
> **Mediator Verdict: CLEAN / NO THREAT DETECTED**

That string is then handed to the verdict LLM as `Negotiation History: [AgentArgument(agent_name='Mediator', finding='Resolved: ... no malicious activity ...', confidence_score=1.0)]`. The judge then has to contradict the mediator to flag Malware — which it only manages because of the YARA hit + the LTM priors.

**Fix.** Distinguish "agreement confidence" from "verdict signal". The mediator should never emit verdict prose (`CLEAN / NO THREAT DETECTED`); its output should be limited to *contradictions found* and *consensus confidence in agent agreement*. Verdict decision should remain solely with the judge LLM. Edit the mediator system prompt to forbid verdict statements.

### LIVE-01 (LOW) — Live tab does not back-fill events on page load

**Evidence.** Opening `/analysis/ff85bf38-…/live` 6 minutes into the running job showed:
- "Waiting for worker to pick up job…"
- Agent Status: "Waiting for the worker to pick up this job…"
- Event Log: "Waiting for events…"

But the worker had been running for 6 minutes and was actively pushing to `analysis:ff85bf38-…` (Redis pubsub channel has 1 subscriber, confirmed via `redis-cli pubsub numsub`).

**Root cause.** WebSocket subscribes to live broadcast but has no replay. Events emitted before the page mounted are lost.

**Fix.** Add a REST endpoint `GET /jobs/{id}/events` that returns historical events (we'd need to persist them — either in a Redis Stream or a `pipeline_events` JSONB column). On Live page mount, fetch history first, then attach WS for future events. Less invasive alternative: subscribe to a Redis Stream (XADD on publish, XREAD on subscribe) which has built-in replay.

### NEG-01 (HIGH) — Worker discards real Triage signatures even when present

**Evidence.** Two consecutive Triage runs of the same sample (CLI: task `260517-r1fcnahz4v`, API: task `260517-spkcxadz3j`) **both** said `0 signatures, 0 TTPs`. The sample is ELF/Go and detonates on Linux VM. Triage *does* analyse it (the task returns `status=reported`), but our parser:
1. Drops the `sample` metadata (T-01)
2. Then somewhere downstream, `signatures` and `ttps` end up empty even though the per-task `report_triage.json` typically has them.

**Speculation requiring code-side verification.** The path is `summary` → `_normalize_report()` → `_enrich_from_overview()` → `_enrich_from_task_reports()`. The `_enrich_from_task_reports` step pulls each child task's `report_triage.json` which is where the signatures live. If `overview` enrichment errored silently ([triage_client.py:678-680](src/maljan/loaders/triage_client.py#L678)), or if the task IDs were never propagated (because the parent `sample` dict was dropped), the per-task fetch never runs.

**Fix.** Two parts:
1. Make `_enrich_from_overview` and `_enrich_from_task_reports` exceptions log at WARNING (currently `logger.debug`) so they surface in dev/CI.
2. Add a smoke test: submit a known-malicious ELF, assert `sandbox_report["signatures"]` has ≥1 entry after enrichment.
